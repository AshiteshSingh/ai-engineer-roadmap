## Mental Model

You evaluate a retrieval-augmented generation system by thinking of it as a two-stage pipeline with two independent failure points. One number cannot diagnose it. A RAG system can fail by retrieving the wrong context, which is a retrieval problem, or by generating an unsupported answer from correct context, which is a synthesis problem. A single end-to-end accuracy score conflates them, telling you something is wrong but not where. So you must factor your evaluation. Measure retrieval quality, meaning did you fetch the right evidence, and generation quality, meaning is the answer faithful to and answering from that evidence, separately. Then attribute every failure to a stage. This gives you the canonical metric quartet, each pinned to a stage. Context precision and context recall judge retrieval. Faithfulness and answer relevance judge generation. Faithfulness, whether every claim traces to the context, is the operationally critical one because it directly measures hallucination. This is evaluation fundamentals specialized to a pipeline. The scorers themselves are an LLM-as-judge that must be calibrated. Failures here are the signal that drives the loops in advanced RAG.

## Why Evaluation Is Hard

Traditional information retrieval evaluation measures retrieval quality using precision, recall, and normalized discounted cumulative gain against relevance judgments. Traditional natural language generation evaluation measures generation quality using metrics like BLEU and ROUGE and human ratings against reference texts. RAG evaluation must assess both simultaneously, plus the interaction between them. Consider a system that retrieves the correct document but generates an answer that contradicts it. That is a synthesis failure. Or one that retrieves irrelevant documents but generates a plausible-sounding answer from parametric knowledge. That is a retrieval failure masked by hallucination. Or one that retrieves relevant documents but overloads the context with noise, causing the large language model to miss the key information. That is context poisoning. Each failure mode is invisible to metrics that evaluate only one stage. The retrieval strategies themselves, including hybrid search, reranking, and HyDE, each introduce distinct failure surfaces. A comprehensive RAG evaluation framework must assess four layers. Retrieval quality asks whether you found the right documents. Context relevance asks whether the retrieved documents are actually useful for answering the question. Faithfulness asks whether the generated answer is grounded in the retrieved context. Answer correctness asks whether the final answer is actually correct.

## The RAGAS Framework

RAGAS, which stands for Retrieval Augmented Generation Assessment and was introduced by Es and colleagues in 2023, provides the most widely adopted automated evaluation framework for RAG systems. It defines metrics for each layer of the evaluation stack and provides LLM-based implementations that do not require ground truth reference answers. These LLM-based metrics are instances of the LLM-as-judge pattern. Faithfulness measures whether the generated answer is supported by the retrieved context. A faithful answer contains only claims that can be verified against the provided documents. RAGAS measures faithfulness by first extracting individual claims and statements from the generated answer. Then for each claim it checks whether that claim can be inferred from the retrieved context. Faithfulness equals the number of supported claims divided by the total number of claims. A faithfulness score of one point zero means every claim in the answer is supported by the retrieved context. A score between zero point five and zero point nine means some claims are supported while others are hallucinated or come from parametric knowledge. A score below zero point five means the answer is largely unsupported by the retrieved context. A low faithfulness score with a correct answer suggests the model is using parametric knowledge rather than the retrieved context. That is a problem because parametric knowledge may be outdated or wrong for other queries.

Context relevance evaluates the quality of the retrieved documents relative to the question. Context precision asks what fraction of the retrieved documents are actually relevant. High precision means all retrieved documents are relevant. Low precision means many irrelevant documents were retrieved, adding noise to the context. Context recall asks what fraction of the information needed to answer the question is present in the retrieved context. Context recall requires a ground truth answer to compute. It checks if every statement in the ground truth can be attributed to the context. Answer relevance measures whether the generated answer actually addresses the question asked. An answer might be faithful, fully supported by context, but irrelevant because it answers a different question than what was asked. RAGAS measures this by generating synthetic questions from the answer and computing the similarity between those generated questions and the original question. If the answer is relevant, the generated questions should be similar to the original. Answer correctness compares the generated answer against a ground truth reference. This requires labeled data but provides the most definitive quality signal. The score reflects both factual accuracy and completeness.

## Building an Evaluation Dataset

The quality of your evaluation is bounded by the quality of your evaluation dataset. There is no shortcut here. The gold standard is manual curation where domain experts create question-answer-context triples. Each entry in your evaluation set should include the question, the ground truth answer, the ground truth contexts that contain the answer, a difficulty rating, a category, and a source. You want diverse question types including factual, inferential, and comparative questions. You want varying difficulty with easy questions that come from a single document with an explicit answer, medium questions that require synthesis, and hard questions that are multi-hop or implicit. You also need negative examples, questions that cannot be answered from the corpus, to test the system's ability to say that it does not know. As the document corpus changes, your evaluation questions must be refreshed. For bootstrapping, you can generate evaluation questions from your documents using an LLM. You can write a function that takes a document and a number of questions, and returns a list of question-answer-context triples. The system prompt instructs the LLM to generate diverse question types including factual, inferential, and comparative, and to return the results as structured data. For your evaluation dataset to be statistically significant, you need at least one hundred questions and ideally five hundred or more for robust evaluation.

## Common Failure Modes

Retrieval failures occur when the wrong documents are retrieved. This is the most basic failure. The embedding similarity between the query and the correct document is lower than between the query and irrelevant documents. You can diagnose this by checking whether expected documents were found and at what rank. If they were not found, you compare the similarity of the expected document to the query against the similarity threshold of the last retrieved result. You also check whether it is a chunking issue by looking at individual chunks of the expected document. Common causes include vocabulary mismatch where the query uses different terminology than the document, chunking issues where the relevant information is split across chunks diluting the embedding, and embedding model limitation where the model does not understand the domain. Sometimes the correct document is retrieved but the wrong chunk is used. The document is in the corpus but the chunk containing the answer scored lower than other chunks from the same document. To fix this, you improve your chunking strategy, add parent-child relationships, or use document-level retrieval with chunk-level reranking. Multi-hop and agentic retrieval approaches can also recover from single-stage retrieval misses by iteratively refining the search.

Synthesis failures occur when the LLM hallucinates despite having correct context. The model generates claims not supported by the retrieved documents even when the documents contain the correct information. You can detect hallucination by using an LLM to analyze each claim in the answer and classify it as supported, unsupported, or partially supported based on the provided context. Common causes include insufficient instruction where the system prompt does not strongly enough instruct the LLM to only use provided context, parametric knowledge leakage where the LLM's pre-training knowledge overwrites the context, and ambiguous context where multiple documents provide conflicting information. Another synthesis failure is when the answer is too vague or generic. The LLM produces a safe but unhelpful response even with relevant context available. This can happen because of the lost in the middle effect where relevant information is in the middle of a long context where LLM attention is weakest. It can also happen from context overload where too many documents dilute the signal, or from poor prompt engineering where the generation prompt does not encourage specificity.

Context poisoning is when adversarial or outdated content exists in the retrieval corpus. If the corpus contains incorrect, outdated, or intentionally misleading content and that content is retrieved, the LLM will faithfully reproduce the incorrect information. This is particularly insidious because the answer will score well on faithfulness since it accurately reflects the context, but will score poorly on correctness. Defenses include source quality scoring where you weight retrieval results by source authority, temporal recency weighting where you prefer newer documents especially for fast-changing topics, and cross-reference verification where you retrieve from multiple independent sources and check for consistency.

## Debugging RAG Pipelines

Every RAG query should produce a trace that you can inspect for debugging. A trace captures the query, a timestamp, the query embedding, the retrieval strategy, the retrieved documents with their IDs, texts, scores, and metadata, the retrieval latency, the reranked documents and latency if applicable, the generation stage details including prompt tokens, completion tokens, latency, and the generated answer, and finally the evaluation scores computed post-hoc or in real-time. You can build a debugger that analyzes a trace for common issues. It checks whether all retrieved documents have low similarity scores, which would indicate a retrieval problem. It checks for duplicate chunks by looking at the ratio of unique texts to total texts. If the ratio is low, you have overlapping chunks and should review your chunking strategy and add deduplication. It checks whether the faithfulness score is low, which would indicate the answer is not well-grounded in the retrieved context and you should strengthen grounding instructions in the system prompt. Beyond individual trace debugging, aggregate analysis reveals systematic issues. You group failures by category. Retrieval failure means low context recall. Synthesis failure means low faithfulness despite good retrieval. Relevance failure means the answer does not address the question. You analyze each category to find common patterns and example queries. This systematic approach lets you identify which component of your pipeline needs improvement.

## A/B Testing Retrieval Changes

RAG systems evolve continuously. You might try new embedding models, different chunking strategies, or updated rerankers. A/B testing is essential for validating that changes actually improve the system. For online A/B testing, you implement deterministic routing based on user ID for consistency. You hash the user ID and use that to assign a user to either the control or treatment variant. You collect metrics for both variants including the query, latency, number of documents retrieved, and user feedback. After collecting enough data, you analyze the results statistically. You compare the positive feedback rate between control and treatment to compute the lift. You always run offline evaluation before exposing users to changes. You compare two pipelines on the same evaluation dataset by running both pipelines on every question, evaluating both answers using the same metrics, and then aggregating the results. For each metric, you compute the mean for control and treatment, the delta, the p-value from a paired t-test, and the counts of improved, degraded, and unchanged queries.

In your A/B tests you need primary metrics, secondary metrics, and guardrail metrics. Primary metrics include user satisfaction measured by thumbs up or down, task completion rate for task-oriented RAG like customer support, and follow-up question rate where lower is better because it indicates the first answer was sufficient. Secondary metrics include latency at the 50th, 95th, and 99th percentiles, token usage as a cost proxy, and retrieval diversity measured by whether you return results from diverse sources. Guardrail metrics that should not degrade include hallucination rate monitored through faithfulness scores, the rate at which the system says it does not know, and error rate from system failures or timeouts.

## Continuous Evaluation in Production

The most valuable evaluation signal comes from users. You need to design feedback mechanisms that are low-friction. For implicit feedback, you collect signals from user behavior. A copied answer is a positive signal. A reformulated query is a negative signal. A clicked source indicates engagement. Time spent on the answer indicates engagement. An abandoned query is a strong negative signal. For explicit feedback, you provide thumbs up or down, optional free-text corrections, and fields for what information was missing or what was incorrect. A production RAG monitoring dashboard should track real-time metrics like query volume, latency distribution, and error rate. On a daily basis you track average faithfulness, relevance, and correctness scores from sampled queries. On a weekly basis you run systematic failure analysis, check retrieval coverage gaps, and review feedback trends. For every change you run a before and after comparison on your evaluation dataset.

You can implement lightweight production monitoring with sampling. You sample a fraction of live traffic and compute automated metrics like faithfulness on those sampled queries. You log those metrics to your monitoring system with tags for the retrieval strategy and document count. You set up alerts for degradation, for example if faithfulness falls below zero point three you fire an alert with the query details. This sampling approach keeps cost manageable while still catching regressions. Failures you find in production feed back into your offline regression set, closing the evaluation loop.

## Alternative Evaluation Frameworks

RAGAS is the most cited RAG evaluation framework but it is far from the only option. Several production-grade alternatives have emerged, each with distinct strengths. The right choice depends on your deployment context, existing infrastructure, and the specific quality dimensions you need to track. DeepEval is an open-source evaluation framework that emphasizes unit-test-style assertions for LLM outputs. Where RAGAS focuses on metrics, DeepEval focuses on test cases. You define pass-fail thresholds and run evaluation suites like conventional test suites. You specify a faithfulness metric with a threshold of zero point seven and an answer relevancy metric with a threshold of zero point seven, then assert that a test case passes both metrics. DeepEval's test-oriented design integrates naturally into continuous integration and continuous delivery pipelines. It also provides a broader set of built-in metrics than RAGAS, including hallucination detection, toxicity, and bias scoring. Use DeepEval when you want to treat evaluation as part of your test suite rather than as a separate analytics workflow.

TruLens provides a feedback-function abstraction that decouples what you measure from how you measure it. Each feedback function can be backed by an LLM judge, a BERT-based scorer, or a custom function. TruLens wraps your RAG pipeline and intercepts calls to record full traces alongside feedback scores. The key differentiator is its instrumentation layer. TruLens can wrap LangChain chains, LlamaIndex query engines, and custom pipelines with minimal code changes, recording every intermediate step. This makes it particularly strong for debugging because you get a full trace of what was retrieved, what was sent to the LLM, and what was returned, alongside quality scores at each stage. Use TruLens when you need deep instrumentation of an existing LangChain or LlamaIndex pipeline and want a visual dashboard for trace-level debugging.

Langfuse is an open-source observability platform that combines tracing, evaluation, and prompt management. Unlike the other frameworks, Langfuse is primarily an observability tool that happens to support evaluation, rather than an evaluation framework that happens to support observability. Langfuse's evaluation support includes LLM-as-judge scoring, user feedback collection, and annotation queues for human evaluation. Its main strength is production monitoring. It captures traces from live traffic, allows you to score a sample of queries using LLM judges, and tracks quality metrics over time. The prompt management layer lets you version prompts and link quality regressions to specific prompt changes. Use Langfuse when your primary need is production observability with evaluation as a component, especially if you want an open-source alternative to commercial LLM observability platforms.

Phoenix by Arize AI bridges ML observability and LLM evaluation. It provides embedding-based analysis that lets you visualize retrieval results in embedding space to understand why certain queries retrieve the wrong documents. Phoenix also supports LLM-as-judge evaluation with built-in templates for faithfulness, relevance, and hallucination detection. Phoenix stands out for its drift detection capabilities. In traditional machine learning, data drift degrades model performance. In RAG systems, document corpus drift from new documents, updated content, or changed terminology can silently degrade retrieval quality. Phoenix can detect when the distribution of query embeddings diverges from the distribution of document embeddings, flagging retrieval degradation before it manifests as user complaints. Use Phoenix when you need embedding-level analysis of retrieval quality, drift detection, or integration with broader ML observability workflows.

In practice these tools are complementary rather than exclusive. A common pattern is to use RAGAS or DeepEval for offline evaluation during development and Langfuse or Phoenix for production monitoring.

## LLM-as-Judge Reliability

Every LLM-based evaluation metric in the frameworks above relies on an LLM judge. This introduces a fundamental dependency. Your evaluation is only as reliable as the judge model. Several specific failure modes arise when applying LLM judges to RAG evaluation. Faithfulness overestimation with paraphrasing is one. LLM judges tend to mark paraphrased claims as supported even when the paraphrase subtly changes the meaning. A RAG answer that says the policy was enacted in twenty nineteen when the context says the policy was proposed in twenty nineteen may receive a high faithfulness score because the overall sentence structure is similar. This is especially dangerous for domains where precision matters, such as legal, medical, or financial contexts. Self-consistency bias is another failure mode. When the judge model is the same model or model family that generated the answer, it tends to rate the answer more favorably. This creates a systematic upward bias in faithfulness and relevance scores. You mitigate this by using a different model family for judging than for generation, or by using multiple judge models and taking the minimum score.

Length and fluency bias is also a problem. LLM judges consistently prefer longer, more fluent answers even when the shorter answer is more accurate. In RAG evaluation, this means a verbose hallucinated answer may score higher than a terse faithful one. Structured evaluation rubrics that force the judge to evaluate claim by claim, as RAGAS does for faithfulness, partially mitigate this but do not eliminate it. Domain knowledge leakage occurs when the judge model has parametric knowledge about the topic. It may mark claims as supported by context because they are factually true even if the context does not actually contain that information. This inflates faithfulness scores and masks retrieval failures.

No LLM-based evaluation should be deployed without calibration against human judgments. The calibration process has several steps. First, collect a calibration set of one hundred to two hundred representative RAG outputs and have domain experts score them on the same dimensions your LLM judge uses including faithfulness, relevance, and correctness. Use the same scale. If the LLM judge outputs zero to one continuous scores, have humans use a one to five Likert scale and normalize. Second, compute agreement metrics like Cohen's kappa or Kendall's tau between human and LLM scores. For RAG faithfulness evaluation, published benchmarks report Cohen's kappa of zero point five to zero point seven between GPT-4 class judges and expert annotators. That is moderate to substantial agreement but far from perfect. Third, identify systematic disagreements. Partition the cases where human and LLM scores diverge by more than one standard deviation and look for patterns. Does the LLM judge consistently overrate answers on certain topics? Does it fail to catch certain types of hallucination? Fourth, calibrate or adjust based on the disagreement analysis. You might adjust the judge prompt by adding domain-specific rubric examples, adjust the score thresholds if the LLM judge is systematically lenient, or flag certain query categories for mandatory human review.

Several RAG-specific calibration techniques exist. Claim-level calibration means rather than calibrating at the answer level you calibrate at the claim level. Extract claims from fifty answers, have humans label each claim as supported or unsupported, and measure the LLM judge's claim-level precision and recall. This gives a more granular view of where the judge fails. Adversarial calibration examples involve creating synthetic test cases designed to fool the judge. Include answers with subtle factual modifications, answers that are correct but unsupported by context, and answers that faithfully reproduce incorrect context. These adversarial cases stress-test the judge and reveal its blind spots. Multi-judge ensembles involve running the same evaluation through two to three different judge models and flagging cases where judges disagree. Disagreement is a strong signal that human review is needed. The ensemble agreement rate also serves as a confidence score for each evaluation.

## Evaluating Agentic RAG

Standard RAG evaluation assumes a single retrieval step followed by a single generation step. Agentic RAG systems where an LLM dynamically decides what to retrieve, when to retrieve, and whether to iterate break this assumption. The evaluation challenge is no longer just whether the system produced a good answer but whether the system took a good path to the answer. For multi-step retrieval evaluation, you need to assign quality scores to each intermediate step. Each step has a type such as query reformulation, retrieval, rerank, filter, or synthesize. For each step you capture the input state, the action the agent decided to take, the result produced, whether the step was necessary according to a human annotator, and whether the step moved toward the answer according to a human annotator.

You evaluate both the answer and the path taken to reach it. For answer quality you use standard metrics like answer correctness and faithfulness. For trajectory quality you compute trajectory efficiency, which is the number of necessary steps divided by the total number of steps. You also measure whether the agent recovered from mistakes by counting how many times an incorrect step was followed by a correct step. You track the total retrieval calls, total tokens used, and total latency. For systems that involve tool selection, such as choosing between vector search, SQL queries, API calls, or web search, your trajectory evaluation must also assess tool selection quality. Tool precision asks when the agent chose to use a tool, was it the right tool for that subproblem. Tool recall asks were there steps where the agent should have used a tool but did not. Ordering efficiency asks did the agent sequence its tool calls in a logical order or did it waste steps on redundant or out-of-order operations. Termination quality asks did the agent stop retrieving when it had sufficient information or did it continue unnecessarily, wasting tokens and latency.

These trajectory metrics are more informative than answer-only metrics for improving agentic RAG systems because they identify which component of the agent loop needs improvement, whether the retrieval strategy selection, the stopping criterion, or the synthesis step. Human annotation of trajectories is expensive. Labeling one hundred multi-step trajectories may take ten to twenty hours of expert time. Two pragmatic shortcuts exist. First, annotate only disagreement cases. Run automated answer-level evaluation first and only annotate trajectories where the answer was wrong or where automated metrics diverge. This focuses human effort on the cases that matter. Second, use LLM judges for trajectory assessment. An LLM can assess whether a retrieval step was necessary or whether a query reformulation improved the search, though with lower reliability than human annotators. Use LLM trajectory judgments as a first-pass filter and human annotation as the gold standard for a calibration subset.

## Evaluation Economics

LLM-based evaluation is not free. Running RAGAS faithfulness evaluation on a single query-answer pair requires one or two LLM calls for claim extraction and claim verification, each consuming tokens. At scale, evaluation costs can rival the cost of the RAG system itself. A rough cost model shows that running the full suite of four metrics on one thousand items using GPT-4o costs approximately thirty dollars. For a production system handling one hundred thousand queries per day, evaluating every query with the full suite would cost approximately three thousand dollars per day, which is clearly impractical. This makes evaluation economics a first-order design concern.

Several strategies exist for reducing evaluation cost. Sampling is the most straightforward approach. Evaluate a random sample of production queries rather than every query. Statistical power analysis determines the sample size. To detect a five percent change in faithfulness with ninety-five percent confidence, you need approximately fifteen hundred evaluated samples. To detect a ten percent change, approximately four hundred samples suffice. For monitoring to detect large regressions, one hundred to two hundred daily evaluations are often adequate. Stratified sampling improves efficiency by sampling more heavily from query categories with historically lower scores or higher variance. Cheaper judge models are another strategy. Not every evaluation requires GPT-4o. For many RAG evaluation tasks, smaller models provide sufficient discrimination. You can implement a tiered evaluation where you use a cheap model like GPT-4o-mini, which is approximately ten times cheaper, for screening and an expensive model like GPT-4o for precision on borderline cases. You run the cheap model first. If the score falls in a borderline range, you run the expensive model for a precise judgment. If the score is clearly high or low, you trust the cheap model. This tiered approach typically reduces evaluation cost by sixty to eighty percent while maintaining quality for the cases that matter most, the borderline ones where a wrong evaluation judgment would lead to incorrect system decisions.

Caching evaluation results is another strategy. Many RAG systems produce identical or near-identical answers for similar queries. You cache evaluation results keyed on the context hash and answer hash to avoid re-evaluating equivalent outputs. For systems with stable document corpora, this cache hit rate can be substantial. Offline batch evaluation means rather than evaluating in real-time, which adds latency and cost to every query, you run evaluation in daily or hourly batches. This allows you to use spot instances or lower-priority API tiers and to aggregate results for trend analysis rather than per-query alerting. You reserve real-time evaluation for critical-path quality gates, such as before surfacing answers on high-stakes topics. Metric selection is also important. Not every query needs every metric. Faithfulness is the most operationally critical metric for most RAG systems because it directly measures hallucination. Context recall requires ground truth and is therefore better suited to periodic offline evaluation. Answer relevance is most useful during development and A/B testing. Choosing which metrics to run on which queries reduces cost without sacrificing coverage of the dimensions that matter most.

## Runtime Internals

The factored two-stage model hides the mechanics that make RAG evaluation actionable. Faithfulness is not a holistic score. The runtime decomposes the answer into atomic claims and then checks each against the retrieved context using entailment or an LLM judge. The score is supported claims divided by total claims. This pinpoints which sentence hallucinated, not just that the answer is bad. Sentence-level scoring would miss a mixed sentence with one true and one fabricated clause. Given a wrong final answer, the runtime localizes the fault using a decision tree. Was the right document in the corpus at all? Was it retrieved? Was it in the top-k passed to the model? Did the model use it? Each no points at a different fix. The fix could be in ingestion, the retriever, the reranker, or the prompt. Skipping this tree leads teams to tune the model when the bug was a missing chunk.

Offline metrics need ground truth. Production has none. The runtime samples a fraction of live traffic and runs reference-free metrics. Faithfulness needs only the answer and the context, no gold standard. It alarms on a moving-window drop. The cost knob is the sample rate. Judging one hundred percent of traffic doubles your spend. Failures from production feed back into your offline regression set, closing the evaluation loop. Every RAGAS-style metric is an LLM-as-judge call and inherits its biases and noise. The runtime safeguard is to calibrate the judge against a human-labeled RAG set to measure agreement. You use a strong judge for faithfulness and treat a metric as untrustworthy until its human-agreement clears a threshold. An uncalibrated faithfulness score is a confident number with unknown error.

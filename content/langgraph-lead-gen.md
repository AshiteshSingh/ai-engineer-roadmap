LangGraph in Production: How Lead-Gen Orchestrates 75+ Agentic Graphs

Lead-gen is a sales-intelligence backend built almost entirely on LangGraph. It runs seventy-five-plus specialized StateGraph instances spread across five Cloudflare Container backends (leadgen-langgraph, leadgen-ml, leadgen-scrape, leadgen-outreach, leadgen-research) — discovery, enrichment, scoring, email composition, outreach, research, classification, recruitment intent, ICP fit — all sharing one Neon-hosted AsyncPostgresSaver checkpoint store and one LangSmith tracing pipeline. This page is a guided tour of how that machinery is wired so you can apply the same patterns in your own systems. For framework fundamentals, see LangGraph first.

The tour is structured as a complexity ramp. It opens with the simplest atomic graph in the fleet and walks through seven stages, each one adding a layer of machinery on top of the last. The order is deliberate so the article can be read or narrated linearly — every stage's machinery is grounded in the simpler one before it, and nothing more advanced is referenced until the stage that introduces it.

Mental Model

Most LangGraph tutorials show a single graph with three nodes. Lead-gen shows the opposite end of the spectrum: dozens of graphs that compose, fan out, fan in, and call each other across container boundaries — while every node still writes to a Postgres-backed shared state and every LLM call lands in LangSmith with a cost in US dollars attached.

The system is structured around four loose layers:

1. Atomic graphs — small, single-purpose StateGraphs like classify-paper, score_contact, or country_classify. One to three nodes, deterministic JSON output, no human-in-the-loop.
2. Pipeline graphs — composite graphs like pipeline, product-intel, email-outreach that fan out to many parallel workers and collect results through reducer-merged state slots.
3. Supervisor graphs — graphs that ainvoke other compiled graphs as subgraphs. The product-intel supervisor invokes deep_icp, pricing, gtm, and deep-competitor and tolerates partial failure by recording errors in a subgraph_errors dict instead of crashing.
4. Remote graphs — graphs that live in other containers (leadgen-ml, leadgen-research, leadgen-scrape) and are reached through LangGraph's RemoteGraph adapter with a circuit breaker in front of every adapter call.

Picture the dataflow simply. A single FastAPI handler — the runs-wait endpoint — receives every request and dispatches to the registered graph by assistant id. Two service planes sit alongside every run: Neon for the Postgres checkpoint store, and LangSmith for telemetry. Everything reads and writes through those two services regardless of which layer the work happens in.

Stage A: One Graph, One Node

Anatomy of classify-paper: The Smallest Atomic Graph

If pipeline is the largest composite in the fleet and admin-chat is the smallest tool-use loop, classify-paper is the smallest atomic graph — one LLM call, three output fields, no DB reads, no fan-out. It is the canonical example of the atomic-graph layer named in the Mental Model, and it ships twice in the registry: once as the single-paper classify-paper assistant and once as the batched classify_paper_authors_batch variant. Both live in the same module; the registry resolves the batch variant by pointing at a different module-level symbol and a different builder. This dual-registration pattern is the registry's accommodation for graphs that have a one-at-a-time API and a many-at-once API with shared internals.

The single-paper node reads three fields off state — title, abstract, and venue — and returns three fields back: an is_sales_leadgen boolean, a confidence float clamped to the zero-to-one range, and a reasons list capped at three short strings. Title is the only required input; a paper with no title short-circuits to a conservative off-topic verdict with a missing title reason, no LLM call. A paper with a title but no abstract still gets classified — the prompt explicitly instructs the model to classify on title and venue alone when the abstract is missing, which keeps the graph useful for venue-only feeds like a recent-conference index.

Defensive shape-handling runs throughout the node. The classifier uses DeepSeek's flash tier at temperature zero point zero — flash because the question is yes-or-no and reasoning depth would be wasted, temperature zero because the team wants the same paper to produce the same verdict across reruns. If the LLM call itself raises, the node does not propagate — it returns the same off-topic-with-reason shape it would have produced for missing input, embedding the exception class name and the first one hundred and twenty characters of the message as the reason. This is the failure-as-data-not-exception pattern: the caller cannot tell whether the off-topic verdict came from the model or from a crashed model, and that is intentional, because the downstream gating logic treats both cases identically.

The batched variant accepts a list of papers and asks the LLM for one verdict per paper, indexed by a one-based integer matching the input order. The batched path is the production workhorse — it cuts cost by roughly an order of magnitude versus single-paper calls when the model is asked to classify a hundred papers at once — and it ships its own robustness gate. The results array is reconciled against the input list by index; any missing index returns a conservative off-topic verdict so the DB write always covers every input row. The team prefers this to raising on count-mismatch because an LLM that emits ninety-eight verdicts for a hundred-paper batch is a salvageable run, not a failed one.

The text-to-sql Graph: A Stricter Cousin

text-to-sql is the same kind of single-purpose graph as classify-paper, but solved as a four-node deterministic pipeline: understand_question → identify_tables → generate_sql → validate_sql. Where classify-paper makes one LLM call, text-to-sql makes four — one per node — and chains them into a small dataflow. The trade-off is exactly what you would expect — text-to-sql is more predictable than a loop-driven agent and cheaper than a multi-step search, but it cannot recover from a missing-table answer the way a tool-use loop can.

Three details survive from the implementation that operators use to debug bad SQL output. understand_question truncates the input to 4000 characters and asks the LLM to restate the question as a single-sentence intent — this normalizes "show me everything about companies that have at least 10 employees and have been added in the last 30 days, sorted by add date" into "Recently-added companies with ≥10 employees, by date." identify_tables truncates the schema to 8000 characters and asks for an exact-name list of tables — the LLM's tendency to invent plausible table names is the second-most-common failure mode, behind hallucinating columns. generate_sql adds a per-prompt rule the operators learned to enforce explicitly: "Prefer explicit column lists over SELECT all-columns. Add a LIMIT 100 unless the question implies an aggregate." The validate_sql node is a hard block — any forbidden write token (insert, update, delete, drop, alter, truncate, grant, revoke) returns {"sql": "", "explanation": "Rejected: non-SELECT statement.", "confidence": 0.0}. The caller still has to execute the resulting SQL through an enforced SELECT-only path; the graph's own validation is a tripwire, not a sandbox.

The graph returns {sql, explanation, confidence, tables_used}. The confidence field is the LLM's own — it is calibration-free and operators learn to treat anything below ~0.6 as "look at the SQL before running it."

Anatomy of the email_compose Graph

email_compose_graph is the longer-form drafting graph used by the auto-apply pipeline and the GraphQL compose-email mutation. It is structurally different from email_outreach_graph — three nodes, no DB reads, no persona matching, no template selection — and its job is to take a context blob and turn it into a polished cold email. Where email-outreach is "pick the right template and substitute fields," email_compose is "write the email from scratch with editorial care."

The graph has three nodes. The first, gather-context, is a pure transformation: it concatenates the recipient name, company name, recipient context, and an optional LinkedIn post text into a single context-summary string. If none of those fields are populated, the node writes the literal string "No additional context." into state. Defensive fallthrough; the draft node always has something to read.

The second node, draft, calls DeepSeek's standard tier at temperature zero point five. The system prompt is selected at runtime by the sender-mode field on state — defaulting to "job-seek" for backwards compatibility with the auto-apply pipeline, switching to "sales-collab" when the operator wants a B2B-partnership voice. Both prompts demand strict JSON output with a subject and body. The draft also forbids four standard AI-marker openers: "I hope this finds you well," "Just wanted to reach out," "I came across your," and "I wanted to reach out." These are the openings spam filters have been trained on; cutting them at draft time saves the refine pass a full retry.

The third node, refine, is where the editorial care lives. It runs DeepSeek standard again — this time at temperature zero point two, so the polish is conservative — with a different system prompt that lists seven rules: strip the AI-marker phrases, cap the opening paragraph at three sentences, cap the subject line at fifty characters and demand it anchor on the recipient's domain, preserve the recipient-name placeholder exactly, preserve the sender's signature block exactly, keep the email's intent and call-to-action intact, and cut filler phrases like "I'd love to" or "I just wanted to."

The refine node also runs a small marker-detection retry loop. After the first refine pass, it scans the refined body for any of the AI markers that should have been stripped. If any are still present, it calls refine a second time with the offending phrases listed explicitly as an additional constraint. After the second attempt, the graph accepts whatever it has and proceeds — two refine passes are the cap, because a third pass against the same marker set would just be the LLM relitigating the same edit it already chose not to make. The refine output is validated through a pydantic schema with a subject between three and seventy characters and a body of at least twenty characters; a validation failure surfaces as a clear error rather than as a confusingly-truncated draft.

Telemetry from both LLM calls accumulates into the graph-meta slot under node names — "draft" and "refine" — so the cost-per-node breakdown shows operators exactly how much polish actually costs versus the initial draft.

Stage B: Single Graphs With State

Those three graphs share a property: their state is small enough to fit on one screen. Once state grows — once a node has to call a tool, branch on confidence, or stream progress to a UI — the graph needs more machinery. The next six examples add exactly that.

Tool-Use Agent: The admin-chat Graph

Most graphs in the fleet are deterministic dataflows — they call the LLM with a fixed shape and route the response through a fixed sequence of nodes. The admin-chat graph is the exception: it implements a small tool-use loop inside a single node, capped at six steps, with three database tools the LLM can call. This is the smallest possible "real" agent in the codebase and a useful counterpoint to the deterministic graphs from Stage A.

The state is two-slot: prompt holds the operator's question and response holds the answer. One node, chat, runs the entire loop. It strips and validates the prompt, builds an LLM client, seeds a transcript list with the user's question, and then loops up to six times. Each step calls the LLM with the system prompt, the tools documentation, and a step-instruction that demands JSON output in one of two shapes. If the LLM's reply contains an answer key, the node returns the answer and exits. Otherwise it dispatches the requested tool with its arguments, appends the tool name, arguments, and returned observation to the transcript, and continues to the next step.

The LLM is prompted to return JSON of exactly two shapes — {"tool": ..., "args": ...} or {"answer": ...} — and the loop terminates the moment answer appears. Three tools are wired:

count_rows(table) — SELECT count() FROM {table} with the table name quoted through psycopg.sql.Identifier. The table name is also gated by _TABLE_IDENT_RE.match(...) so an LLM-supplied value that fails the regex never reaches the SQL string. Two layers of defense against LLM-driven SQL injection: regex first, then SQL identifier quoting.
inspect_schema(table) — reads information_schema.columns with the table name passed as a query parameter (not an identifier substitution, because information_schema is queried by string equality on table_name). Same regex gate.
query_db(sql) — the dangerous one. Three nested defenses: a startswith("select") check, a substring deny-list (insert, update, delete, drop, alter, truncate, grant, revoke, ;--), and — most importantly — a transaction-scoped SET LOCAL TRANSACTION READ ONLY plus SET LOCAL statement_timeout = '5s'. The deny-list is bypass-prone (CTE-RETURNING, comment tricks, pg_read_file), so the read-only transaction is the real safety net. fetchmany(MAX_ROWS=50) caps the result size; the formatted output is "header | row1 | row2 ..." plain text.

The _dispatch function is a small router that pattern-matches the tool name and returns its string output to the LLM. Errors come back as "Error: <message>" strings so the LLM can see them and adapt — this is the agentic-feedback channel that lets the LLM recover from "table X does not exist" by calling inspect_schema to find the real name.

The six-step cap is the only hard termination guarantee. A confused LLM that never emits answer will run six tool calls and then fall through to {"response": ""} — a deliberate "no answer is better than a runaway loop" trade-off. Each step's telemetry is accumulated locally (acc_tokens, acc_cost) and surfaced through agent_run_span / tool_call_span helpers in langsmith_setup, which stamp the step count and totals on the run-tree in LangSmith so a degenerate loop is one query away from "this question cost $0.12 in six tool calls and never converged."

Anatomy of the company_discovery Graph

The pipeline's first phase is company_discovery, the graph that turns a fuzzy seed query like "AI consultancies in Europe doing RAG" into a list of company-candidate rows in Neon ready for enrichment. Six nodes, two distinct entry paths, and one subtle blocklist gotcha that the team documents inline because it tripped up the earlier integration.

The six nodes are expand-seed, seed-from-ashby, brainstorm, dedupe, pre-score, and persist. Expand-seed runs DeepSeek's deep tier at temperature zero point two to extract four facets from the seed query — a vertical name, a geography string, a size band drawn from a fixed five-value enum (seed, startup, smb, midmarket, enterprise), and a keywords list. If the caller already supplied both vertical and keywords on input state, expand-seed short-circuits and returns immediately — a small but load-bearing optimization that lets ops pre-fill the facets and bypass the LLM expansion entirely.

Two parallel paths feed the brainstorm step. The first, seed-from-ashby, pulls companies from the Ashby ATS slugs table whose verticals match the expanded facets — a deterministic, zero-LLM lookup that runs whenever the operator wants reproducible discovery against a known company universe. The second, brainstorm, asks DeepSeek to invent twelve to twenty real companies that fit the facets, emitting each as a name, domain, and one-sentence "why" string. The brainstorm path is the higher-recall option; the Ashby-slug path is the higher-precision option. The graph runs both and lets the downstream dedupe step reconcile.

Dedupe is a single SQL round-trip: it selects every canonical-domain in the candidate list that already exists in the companies table, builds a set of those domains, and filters the candidate list to keep only the new ones. The skipped-existing count is stamped onto state so the run report can show "we discovered fifteen companies, twelve were already known." Pre-score is a deterministic keyword heuristic over each candidate's "why" string — zero point four points if the why mentions an AI-related token like ai, ml, llm, genai, agent, rag, or foundation; zero point three if it mentions consult, agency, services, studio, or advisor; zero point two if it mentions remote, distributed, or global; the cumulative score is capped at one point zero and candidates scoring below zero point two are dropped. The scorer is intentionally crude — its job is to filter obvious LLM hallucinations, not to rank order, since the downstream enrichment pipeline does the real scoring.

Persist applies one last gate before the INSERT: the company-blocklist, loaded once per run via asyncio.to_thread so the synchronous DB read does not stall the event loop. The blocklist gate at this layer exists because the pipeline graph's discover node applies its own blocklist on the explicit-domains path, but the LLM-brainstorm path does not pass through that node — so persist re-applies the blocklist as defense in depth. Without it, an LLM that hallucinated a blocked competitor's domain would write the row and the downstream enrichment would discover the bypass only after spending money on it.

ICP Composite Scoring: How Companies Get a Tier

The ICP-fit scorer in leadgen_agent/icp_fit_scorer.py is the deterministic side of the ICP pipeline — the side that turns the LLM's qualitative ICP analysis into a single numeric composite score and one of four tier labels: hot, warm, cold, or disqualified. It is the gate between "we discovered a company" and "we put a contact on it." Almost every downstream filter in the system runs against the composite tier rather than the raw score.

The composite blends four sub-scores using weights named after Greek letters. Alpha, defaulting to zero point three zero, weights the deterministic regex-based vertical score that ran earlier in enrichment. Beta, also zero point three zero, weights the LLM-produced weighted-total from ICP analysis, multiplied by an evidence-match factor. Gamma, zero point two five, weights segment fit. And delta, zero point one five, weights persona fit. The four weights sum to one. They can be overridden by dropping a composite-weights JSON file into the project's config directory; the loader reads it once per process and falls back to defaults on any parse error.

Two thresholds turn the composite into a tier. Hot fires at zero point six six or higher. Warm fires between zero point three three and zero point six six. Cold fires below zero point three three. And the disqualified tier is a special short-circuit driven by deal-breakers: any high-severity deal-breaker hit on the company's corpus collapses the composite to "disqualified" regardless of the four sub-scores. This is the gate the company-QA graph mentioned earlier checks first — a disqualified company never even reaches the QA pass, so the deal-breaker detector is doing both compliance and cost work.

The deal-breaker detector walks each item in the ICP analysis's deal-breakers list, normalizes its severity through a synonym table that maps the LLM's preferred adjectives — "critical," "blocker," "showstopper," "major" — to a canonical "high," and looks for a hit in the company's corpus. The match is hierarchical: first it tries an exact regex match on the deal-breaker name; if that fails, it splits the deal-breaker's reason field into the first four letter-tokens and tries to match any of them. The hierarchy exists because LLM-emitted deal-breaker names are inconsistent — sometimes "uses Salesforce," sometimes just "Salesforce," sometimes "CRM is Salesforce" — and the reason-token fallback catches the ones the name match misses. A successful match returns the deal-breaker name, the normalized severity, and the matched pattern, all of which are surfaced to operators in the run report.

Segment fit and persona fit both score against the company's enrichment payload using a similar shape: a token-hit counter and a fuzzy-ratio helper. The token-hit counter splits a description string on commas, semicolons, pipes, and runs of whitespace, filters tokens shorter than two characters, and counts how many appear as whole-word matches in the company corpus — capped at a configurable max-expected (default three) so a single matching token cannot dominate the score. The fuzzy-ratio helper prefers rapidfuzz's token-set-ratio when available and falls back to a substring-containment heuristic when rapidfuzz is missing. The same dual implementation appears in the email-outreach persona matcher; both modules use it for the same reason — rapidfuzz ships native code that does not always build cleanly in Cloudflare Containers.

The composite-score path is one of the only places in lead-gen where deterministic arithmetic decides what happens to a company. Everywhere else the LLM has the last word; here the LLM contributes one of four sub-scores and the rest is regex and weighted summation. Operators who want to debug "why is this company cold?" read the four sub-scores in the run telemetry and see immediately which leg is dragging the composite down — a clarity you do not get when the same decision is wrapped inside a single LLM call.

Pattern 1: Send-Based Fan-Out with Merge Reducers

The most reused pattern in the codebase is the four-step shape: queue, Send, worker, collector. The pipeline graph illustrates it cleanly. The enrich-queue node emits a list of Send instructions — one per company id — each pointing at the enrich-one worker. LangGraph schedules every enrich-one invocation concurrently, then routes them all to a fixed enrich-collect node. To keep the parallel writes from colliding, the state fields that workers write to have a merge reducer attached. In code, that means the state typed-dict declares two fields — the enrich-results dict and the contacts-results dict — each annotated with a simple merge-dict function that spreads two dicts together into a new one. A third field, graph-meta, carries a slightly fancier merge function that knows how to fold per-node telemetry.

Each enrich-one worker returns a dict containing a single key — its own company id — mapped to its payload. LangGraph routes those returns through the merge-dict reducer so the final state ends up with one big dict containing every worker's result, indexed by id. No locking, no invalid-concurrent-graph-update exception, and no need for workers to know about each other. The same shape powers the deep-competitor graph, where six specialist nodes fan into a single synthesize collector, and the product-intel v2 supervisor covered later.

The price of this pattern is unbounded concurrency. LangGraph itself doesn't cap the number of Sends — that gate sits at the HTTP layer instead. Dispatch routes like the positioning-all endpoint wrap their background tasks in an asyncio semaphore, tunable via the positioning-concurrency env var with a default of three, so the upstream LLM provider doesn't rate-limit the whole fleet.

Pattern 5: Telemetry as a First-Class Channel

Every LLM call in lead-gen goes through the ainvoke-json-with-telemetry helper in the llm module, which returns the parsed JSON and a telemetry dict carrying six fields: the model name, input tokens, output tokens, total tokens, dollar cost, and latency in milliseconds. Nodes call it and accumulate the result under their own name. A typical drafting node awaits the helper with its prompt, provider, and schema arguments, unpacks the parsed result and the telemetry dict, and returns both — the parsed draft as the node's primary output, and the telemetry stamped into the graph-meta telemetry slot under the node's own name as a key. The next node down the graph can look at draft-email's telemetry without coupling to draft-email's code, because the key is the node name itself.

Because the graph-meta telemetry slot has a merge reducer attached, telemetry from every node — including parallel Send workers — accumulates without conflict. A terminal node calls compute-totals to roll the per-node numbers into a five-field dict that mirrors to a total-cost-usd column on the product-intel-runs table, added in migration sixty-six. The compute-totals helper walks every entry in the telemetry dict, skips any non-dict entries defensively, and sums four counters: input tokens, output tokens, cost in dollars, and latency in milliseconds. It returns those four sums plus a derived total-tokens field that adds input and output together, with the cost field rounded to six decimal places.

Three details to note. The total-cost field is rounded to six decimal places because DeepSeek prices in fractions of a cent, and the float-noise on summed sub-cent values would otherwise leak into the API response as something like zero point zero zero two three followed by fifteen ones and a three. The total-latency field is the sum across nodes, not the wall-clock — that distinction matters when a graph fans out: ten parallel Send workers contribute their individual LLM latencies into one summed total, which is bigger than the wall-clock the graph actually took. Operators reading the field need to know it captures "compute used" rather than "time spent." And compute-totals returns zeros instead of None when called with a missing telemetry dict, so terminal nodes can call it unconditionally without null-checking.

The retry layer underneath ainvoke_json_with_telemetry is also worth a look. The loop honors three env knobs — LLM_MAX_RETRIES (default 3), LLM_BACKOFF_BASE_S (default 1.0), LLM_BACKOFF_CAP_S (default 20.0) — and applies exponential backoff with full jitter (random.uniform(0, min(cap, base  2  attempt))). A Retry-After header on a 429 or 503 short-circuits the jittered backoff with the server-hinted delay, clamped to the cap so a misbehaving upstream cannot park a worker for an hour. The latency field always reports the total wall-clock across retries — not just the successful attempt — so cost-per-node diagnostics still flag pathologically slow nodes whose total time is dominated by retry backoff rather than by the LLM itself.

_is_retryable_exception is selective: OpenAI SDK APIConnectionError, APITimeoutError, and APIStatusError with retryable status codes (408, 425, 429, 500, 502, 503, 504) all qualify, as do raw httpx.TimeoutException, httpx.ConnectError, and httpx.RemoteProtocolError. Schema validation errors and 4xx prompt-related failures are not retryable — the prompt is the problem and retrying just amplifies cost. This distinction is what kept lead-gen from accidentally hammering DeepSeek when a schema bug caused 422s; the loop returns immediately and the error surfaces to the caller.

The downstream JSON parser, _parse_json, runs a three-step fallback ladder before giving up: strip markdown fences and try json.loads; extract the outermost balanced {...} or [...] span (handles "Here's the JSON: ..." preambles); finally run json_repair to heal unescaped quotes, trailing commas, and truncated output. The function raises json.JSONDecodeError only on truly empty input so callers can distinguish "model didn't respond" from "model responded with garbage" — both fail the run, but only the first is worth retrying.

This is also where the LangSmith integration plugs in. The init-langsmith helper runs once from the FastAPI lifespan before any graph compiles, validating the API key and endpoint URL so a misconfig surfaces in the boot log as langsmith-disabled rather than as silently missing traces hours later. When the tracing env var is set, the LangChain runtime auto-installs a LangSmith callback on every ainvoke and graph.ainvoke without per-graph code changes; when the env var is unset or the key is blank, the tracer is never installed and runs stay hermetic in CI, dev, and sandbox. Because the tracer is wired through the runtime rather than per-call, graph-level traces — state transitions, fan-in and fan-out, Send dispatches, conditional-edge routing — appear in LangSmith alongside the LLM spans without any per-node opt-in. The Stage G interview-prep section walks through the trace shape end-to-end on a real admin-chat run.

The Graph Registry

Every graph lives in one place: the registry module inside the leadgen-agent package. The registry is not a dictionary — it is an immutable tuple of frozen graph-spec dataclasses, ordered for presentation but resolved at runtime by assistant id. The dataclass captures five fields. The first is the assistant id, the public name used at the runs-wait endpoint, in the LangGraph JSON catalog, and in the TypeScript client. The second is the module — a dotted import path, like leadgen-agent dot email-compose-graph. The third is the compiled attribute, defaulting to the literal "graph", which names the module-level symbol referenced from the JSON catalog. The fourth is the builder attribute, defaulting to "build-graph", a callable that takes a checkpointer and returns a compiled graph. And the fifth is a resumable boolean, defaulting to false; it is set to true only when a cron-driven graph needs to resume from a stable thread id.

Two runtimes consume this registry. The local langgraph dev server on port 8002 reads it via a generated core/langgraph.json (produced by backend/scripts/gen_langgraph_json.py — make gen-langgraph-json regenerates it whenever a row is added). The production FastAPI app at core/app.py imports GRAPHS directly and compiles each spec inside its lifespan startup hook. Keeping registry.py import-free of leadgen_agent._graph modules at top level is load-bearing: the JSON generator can enumerate sixty-plus graphs in milliseconds without dragging in optional LLM or DB dependencies that some graph modules import eagerly.

Only the research_loop graph compiles with resumable=True — it owns a stable thread id so the cron tick can resume mid-iteration after a deploy. Every other graph compiles with resumable=False, meaning each runs-wait endpoint call gets a random UUID thread. This is a deliberate decision: it keeps Neon's checkpoint_blobs and checkpoint_writes tables from accumulating write-only garbage from one-shot graph invocations. compile-one in core/app.py passes checkpointer=None for non-resumable graphs, which short-circuits the saver entirely.

The single FastAPI entry point is simple. The runs-wait route receives a POST, looks up the compiled graph by assistant id, builds a config carrying a fresh UUID thread id under the configurable section, and awaits the graph's ainvoke method with the request input and that config. That one handler routes to all sixty-four graphs registered in the leadgen-agent registry. The frontend talks to it through the LangGraph client TypeScript module, which just POSTs JSON. There is no per-graph endpoint — the registry is the dispatch table.

Multi-Registry Topology

The leadgen_agent registry is only one of five. Each Cloudflare Container backend ships its own registry compiled into its own FastAPI app:

backend/leadgen_agent/registry.py — 64 graphs. The main backend (leadgen-langgraph worker). Discovery, enrichment, scoring, email, classification.
backend/ml/ml_graphs/registry.py — 2 graphs. JobBERT skill NER and BGE-M3 embedding service. Built on top of Candle and llama.cpp where possible to avoid Python ML stack bloat in the container.
backend/scrape/scrape_graphs/registry.py — 1 graph. Playwright-based consultancy profile scraper, deployed as leadgen-scrape so its memory footprint and crash surface stay isolated from the main backend.
backend/outreach/outreach_graphs/registry.py — 1 graph. Email outreach delivery and ATS write-back, isolated so a flaky ATS vendor cannot wedge the discovery pipeline.
backend/research/research_graphs/registry.py — 7 graphs. Common Crawl ingest, Arxiv/OpenAlex fetchers, agentic search, GitHub pattern mining, and the research_loop_tick graph that replaced the retired crates/papers Rust pipeline in 2026.

The five registries are not mounted into a single FastAPI app. Each one is a separate Cloudflare Container with its own URL, secrets, and the wrangler config. The main backend reaches the other four through RemoteGraph adapters covered in the RemoteGraph pattern later in this article. This is the boundary that lets the team upgrade torch in leadgen-ml without redeploying the discovery pipeline — and it is the boundary the circuit breaker protects.

compile-one and the Failure-Isolation Loop

The lifespan's compile step deserves a closer look because its behavior is the difference between "one bad graph five-hundreds every endpoint" and "one bad graph is a footnote in the debug state endpoint." The loop is small: it walks every graph spec in the registry, calls a compile-one helper inside a try-except, stores the result under the assistant id on success, and on failure appends a string describing the exception to a failures list while letting the loop continue. It returns both the compiled-graphs dict and the failures list.

Three invariants matter. First, exceptions inside one graph's build_graph(checkpointer) never propagate out of the loop — they land in failures and the lifespan keeps going. The container stays alive; the failed assistant_id simply disappears from app.state.graphs, and the runs-wait endpoint returns a 404 for that id with the rest of the fleet untouched. Second, compile-one enforces the checkpointer-routing rule at the boundary: builder_checkpointer = checkpointer if spec.resumable else None. Non-resumable graphs receive None, which is what stops the checkpoints / checkpoint_blobs / checkpoint_writes tables from filling with random-UUID write-only rows (the original Neon storage-cap blowup that prompted the whole resumable flag design). Third, the import path is importlib.import_module(spec.module) rather than a top-level import — this is what lets registry.py stay dependency-free of leadgen_agent._graph modules even though compile-one will eventually load every one of them.

The pre-compiled escape hatch (builder_attr=None) handles the handful of graphs that build their CompiledGraph at module import time with no checkpointer ever wired. The runtime grabs getattr(mod, spec.compiled_attr) directly. These graphs cannot be made resumable retroactively without a builder, but in exchange they pay zero compile cost on every cold start beyond the import itself.

Stage C: Production Engineering Patterns

Every graph so far has been one cleanly-bounded unit. Production reality breaks that boundary in two ways: connections die mid-run and the workload itself wants to fan out across dozens of parallel workers. The next four sections are the engineering that keeps both honest.

Pattern 6: Connection Pool Engineering

Lead-gen runs the async-postgres-saver against Neon, which serves traffic through PgBouncer with a roughly five-minute idle timeout. A naïve async connection pool drops connections after that timeout, and the next graph call dies with an operational-error reporting unexpected EOF while reading. The fix lives in the core app module. An async-with block opens an async connection pool with five settings: the database URL from the environment, a minimum pool size of one, a maximum of eight, the check-connection function passed as the pool's checkout-validator, and a max-idle of one hundred and eighty seconds — well below Neon's roughly three-hundred-second cutoff. The pool is opened with open-false and an explicit await on its open method afterwards, then the saver is constructed from the pool.

The check-connection setting issues a lightweight SELECT one before every checkout, and the max-idle setting retires sockets before Neon's pooler does. The whole fleet of seventy-five-plus graphs shares this one pool — it sits inside a single async with block that brackets the FastAPI lifespan, so pool teardown is deterministic on shutdown rather than left to garbage collection. It is invisible until something flaps, and then it is the only thing that matters.

This pattern is so load-bearing that it is now memorialized as a feedback memory across both the lead-gen and research-thera backends: every CF Container that talks to Neon must pass check=AsyncConnectionPool.check_connection. The symptom of forgetting it is a 500 from the runs-wait endpoint or /threads/{id}/runs after the container has been idle for five minutes — never a 500 on first call, always after the idle window, which makes it look like an intermittent network blip until the third or fourth occurrence.

Anatomy of the pipeline Graph

The pipeline graph is the most-used composite in the fleet and the best single example of how the patterns combine into one production run. Its state is a typed dict with optional fields and roughly twenty slots, split into three roles. The input slots are the things the caller sets: a seed query string, an optional domains list, an auto-confirm flag, a run-all flag, a per-stage cap, and a QA-critic sample size. The working slots are what nodes write as they go: discovered ids, enriched ids, contact ids, QA issues, outreach candidates, and the approved-outreach ids that the human-in-the-loop step fills in. A second group of working slots — all named with a leading underscore — holds the Send-fanout queues, their started-timestamps, and merge-reducer-backed result dictionaries for both the enrich phase and the contacts phase. The output is a list of one stage report per phase, plus an error string.

The leading-underscore slots are working state — short-lived, written by fan-out workers, drained by the matching collector node, and conceptually invisible to the caller. The unprefixed slots are the run's public output. The two underscore-results slots carry a merge-dict reducer so parallel Send workers do not collide on a concurrent-graph-update exception. And because every slot is optional, the graph tolerates partial state — which is essential for the explicit-domains input path that skips discovery entirely.

Walking the graph from left to right, you pass through five phases. First, discover seeds the run. Next, an enrich phase: an enrich queue node hands work to many parallel enrich workers via Send, and they all merge back into a single enrich collector. After that, a contacts phase: a contacts queue, parallel contact workers, and a contacts collector with the same fan-out-and-merge shape. Then a QA phase, which has two nodes back-to-back — a deterministic counts check, then a reflection critic that catches issues the counts miss. Finally an outreach phase: an outreach queue node that pauses for human approval, and only after the operator resumes does the outreach runner fire. The two fan-out queues both have a special empty-queue path that skips their workers entirely and routes straight to the collector, so a phase with nothing to do still records a clean SKIP report instead of silently doing nothing.

Three things in this graph are worth dwelling on, because they are easy to get wrong if you copy a vanilla LangGraph fan-out tutorial.

First, the dispatch nodes are conditional edges, not nodes. The enrich and contacts dispatch functions are not registered with add-node — they are the second argument to add-conditional-edges, which lets a function return either a list of Send objects to fan out to a worker, or a plain string to route to a single named node. The empty-queue case returns the collector's name as a string, which skips workers entirely and lets the collector record a SKIP stage report. That is cleaner than emitting zero Sends, which LangGraph would happily accept but would leave you with no audit trail.

Second, stage reports accumulate by appending, not by overwriting. Each node that finishes a phase computes a stage-report dict — with fields for stage name, status, processed count, created count, errors, and duration in milliseconds — and returns it appended to the prior reports list. There is no reducer on reports; every node reads the prior list and appends. This works because the pipeline is sequential at the phase boundaries, and fan-out lives strictly between each queue-and-collect pair, which is itself sequential at the outer level.

The discover node has two paths in one body. When state["domains"] is non-empty, the node bypasses company_discovery_graph entirely and inserts canonical domains directly via psycopg.AsyncConnection.connect(_dsn(), autocommit=True). When domains is empty, it delegates to the discovery subgraph with seed_query. This mirrors the --domains FILE flag from the retired Rust CLI and lets operators bypass the LLM brainstorm when they already have a list. The blocklist is loaded once per run via asyncio.to_thread(_blocked_domains_set) so the synchronous DB read does not block the event loop.

Anatomy of the email-outreach Drafting Graph

The drafting graph that the pipeline invokes after the approval gate is the cleanest example of a single-purpose LangGraph in the fleet — eight nodes, one conditional edge, no fan-out, no interrupt(), and a strong "fail open, surface skip_reason" contract that makes it safe to call from anywhere. Reading it end-to-end is the fastest way to see how the LangGraph patterns already covered compose at the small scale.

The drafting graph runs as a single straight line with one branch. It opens with lookup-contact and a check-stop-conditions node back-to-back. From check-stop the one conditional edge in the graph routes either to skip — straight to END — or to continue. The continue path threads through six more nodes: load-product-context pulls the personas and templates, match-persona scores the contact against each persona, select-template picks an outreach template, extract-hook reads a LinkedIn post if one was provided, draft writes the email, and format-html wraps it for delivery before reaching END.

check_stop_conditions is the only conditional edge in the graph. It reads the last ten rows of contact_emails for the contact, sorted newest-first, and walks them looking for reply_received, reply_classification, status, or followup_status values that match the skip set. The first match wins, and the node returns {"skip_reason": "replied" | "bounced" | "unsubscribed" | …}. _route_after_stop_check then routes END if skip_reason is set and load_product_context otherwise. The ten-row history is deliberate — a single stale sent should not mask a later bounced that landed an hour ago. The DB read is wrapped in a try/except that fall-throughs to {"skip_reason": None} on any failure, so a transient Neon hiccup never blocks a draft; the graph fails open by design.

load_product_context reads products.icp_analysis and products.gtm_analysis JSONB columns and extracts personas and outreach_templates arrays from them. Every shape check (isinstance(personas, list), etc.) is defensive; if any cast fails the node returns empty lists and the downstream nodes degrade gracefully into a template-free path. The product-context join is what makes the drafter "product-aware" — without it the draft falls back to a free-form 100-word cold email.

Match-persona is the most numerically-interesting node. It scores each persona against the contact's position, seniority, and department triple with a weighted sum: zero point seven times the title score, plus zero point one five times the seniority score, plus zero point one five times the department score.

The weight ratio is empirical — title alignment is by far the strongest signal for whether a persona is a good match, but seniority and department together still carry enough information to break ties between two similarly-titled personas (a "Head of Engineering" persona scored against a contact with position="Engineering Manager" lands one bucket lower than against position="VP Engineering"). _fuzzy_score prefers rapidfuzz.fuzz.token_set_ratio and falls back to a Jaccard-style set-overlap ratio when rapidfuzz is unavailable — the fallback exists because rapidfuzz ships native code that does not always build cleanly inside Cloudflare Containers.

The match result is cached in contact_persona_scores via an UPSERT keyed by (contact_id, product_id, persona_title), with scored_at = now() stamped on update. A subsequent call to the graph hits the cache first and returns the existing match if score >= threshold (default 0.6) — this is what keeps email-outreach cheap when the pipeline cycles back to the same contact across runs. The cache write is in its own try/except so a DB hiccup degrades to "drafted but not cached," not "draft failed."

The product_aware flag in state captures the threshold check separately from the persona match: when score < threshold, the node still returns the persona match (for telemetry) but flips product_aware=False. The downstream select_template node reads product_aware and short-circuits to template=None, which forces draft onto its free-form 100-word path. This dual-output design — match plus aware-flag — is what lets ops debug "why did this contact get a template-free draft?" by reading state instead of re-running the graph.

select_template picks an outreach template in two passes — first by exact persona-title match, then by channel == "email" fallback. The two-pass structure is robust against templates that omit a persona field; an unspecified persona is treated as a wildcard email-channel template.

extract_hook is the only non-DB node before draft. It runs Mistral-7B-Instruct-v0.2 on Workers AI (provider="email_llm") with a system prompt that asks for one specific, concrete hook from a LinkedIn post (or returns "" if no post was provided). The hook is a single sentence with no quotes — short enough to fit inside a cold email's opening line without overstaying its welcome.

draft is the workhorse and branches twice. If the state has a template (product_aware and select_template both succeeded), the node feeds the template scaffold to the LLM with explicit substitution slots — {{first_name}}, {{company}}, {{hook_from_post}}, {{persona_pain}} — pulled from the contact row and the persona record. The system prompt caps the draft at 120 words, forbids em-dashes, forbids exclamation marks, and demands JSON {subject, body} back. Without a template, the system prompt drops to 100 words and just asks for a "short cold outreach email that references the hook naturally" — same forbidden punctuation, same JSON return shape. The em-dash ban is a tell that operators run the output through their own deliverability heuristics: em-dashes correlate with AI-generated copy in spam filters' training data, and outbound copy that reads like a human carries higher reply rates.

format_html is a pure transformation. It splits the text body on \n\n, escapes each paragraph through html.escape, wraps each in <p> tags, and stamps both text and html slots in state so downstream consumers can use whichever shape they need without re-running the graph. The escape is the only XSS defense in the path; the SMTP / ATS write-back layer trusts the html field as already-safe.

The build wires it all together with one conditional edge and seven plain edges. The graph starts at lookup-contact, flows to check-stop-conditions, and from there the single conditional edge routes either to END on a skip or onward to load-product-context on a continue. From load-product-context the path threads sequentially through match-persona, select-template, extract-hook, draft, and format-html before terminating at END. The graph is a state-graph over a total-false typed-dict state. Every slot is optional, every node tolerates missing predecessors, and the conditional edge is the only place where state actually changes the graph's shape. That combination — defensive nodes, optional state, one routing decision — is why the drafter is reusable from non-pipeline call sites without forcing them through state setup they do not need.

Pattern 4: Human-in-the-Loop with interrupt()

Exactly one graph in the fleet is gated by a human: the pipeline graph. The gate lives in the pipeline's outreach-queue node, which builds an approval queue from the candidates that survived QA and the QA critic, then calls LangGraph's interrupt function to suspend the thread mid-execution. The interrupt's payload carries three fields: a stage name marking it as outreach-approval, the queue itself, and an instructions string telling the resumer what shapes the decision can take. The frontend polls the runs endpoint for status, sees an interrupt event, surfaces the queue to the operator, and sends back a Command-resume to continue. The resolver then normalizes the decision into an approved-candidates list and a note string.

The resumer accepts four shapes: the literal string "approve all," the literal string "reject," a bare list of contact ids, or a dict with an approved-ids key. The resolver normalizes all four shapes into the same approved-list-and-note tuple, so the frontend can stay sloppy without breaking the contract.

The downstream email-outreach graph itself is not interrupt-gated. It is a pure drafting graph — lookup-contact, check-stop-conditions, load-product-context, match-persona, select-template, extract-hook, draft, format-html, END — and it runs once per approved contact after the gate. Splitting the gate from the drafting graph keeps the drafting graph reusable from non-pipeline call sites: the GraphQL compose-email mutation, the paper-author-interview graph, internal smoke tests — without forcing them through an approval flow they don't need.

When the pipeline runs in auto_confirm=True mode (used for synthetic load tests, the dispatch/lead-gen-teams background path, and any cron-driven invocation), the outreach_queue node still builds the queue but short-circuits the interrupt() call and treats every candidate as approved. Both modes live in the same graph — a feature flag, not a separate graph — because the approval bookkeeping (approved_outreach_ids, the outreach_gate stage report) needs to land in state either way for downstream telemetry.

Stage D: Multi-Graph Supervision

A pipeline that fans out is still one graph. The harder move is composition — one supervisor graph invoking other compiled graphs as subgraphs, each able to fail without crashing the parent. The next five examples are the fleet's supervisor patterns.

Pattern 2: Subgraph Composition with Partial-Failure Tolerance

The product-intelligence layer ships two supervisor graphs registered under different assistant_ids. The original product-intel (analyze_product) is a sequential supervisor; the production rewrite analyze_product_v2 is a parallel DAG. The article version exists because the supervisor pattern first landed sequentially, and the v2 rewrite slotted in as a separate assistant so the original API contract kept working — a deliberate two-graph cutover rather than a flag flip.

The v2 DAG starts at a check-freshness subgraph drawn from the freshness graph. From there it branches in two directions. On the fresh branch, the supervisor loads cached outputs, synthesizes a report, and reaches END without doing any new analysis. On the stale branch, the supervisor fans out to three parallel subgraphs — deep-competitor-analysis, run-pricing, and run-gtm — and waits for all three to complete. Their outputs feed into a positioning subgraph that runs after the fan-in, then into a synthesize node that calls the LLM, and finally to END.

Each leg is a fully compiled state-graph with its own checkpointer. The supervisor calls them through await on the subgraph's ainvoke method and catches their exceptions individually. The run-pricing node, for example, is a small async function that opens a try block, awaits the pricing graph with a product-id payload and a fresh-UUID-thread-id config, and on success returns a dict with the pricing field set. On exception, it returns a different dict whose only key is subgraph-errors, mapping the node name to the exception string clipped to five hundred characters.

Three things make this work in production. First, every subgraph writes to a disjoint target — pricing → products.pricing_analysis, gtm → products.gtm_analysis, positioning → products.positioning_analysis, deep_competitor → its own competitor_analyses table family. No two parallel branches ever touch the same target, so write ordering does not matter and you cannot race-condition the supervisor by parallelising it. Second, subgraph_errors: Annotated[dict[str, str], _merge_subgraph_errors] is keyed by subgraph name; partial failures accumulate rather than overwrite, so the synthesize node knows which branches degraded. Third, the imports that hand the subgraphs to the supervisor are wrapped in try/except ImportError blocks with no-op passthroughs (freshness=stale, positioning=empty) so the supervisor still runs end-to-end while neighboring teams ship their graphs in parallel worktrees.

A conditional edge at synthesize checks subgraph_errors and routes either to notify-complete or notify-error. The report ships even when one of the three parallel pillars is missing — useful when, for example, the pricing scraper hits a flaky vendor site. Production-grade orchestration is mostly partial-failure design, and this is where it lives.

Streaming Subgraphs for Progress UIs

Most subgraph invocations in lead-gen use await subgraph.ainvoke(...), which blocks until the subgraph terminates and returns final state. But the product-intelligence supervisors expose a "N of M nodes done" badge to the operator, and rendering that badge needs per-node progress events — ainvoke is the wrong primitive. The fleet handles this through a small shared helper, leadgen_agent/_subgraph_stream.py:stream_subgraph, used by both product_intel_graph (v1) and product_intel_v2_graph so the v1→v2 cutover does not regress the badge.

The helper wraps compiled.astream(inputs, stream_mode="updates") — stream_mode="updates" is the LangGraph stream variant that yields one dict per node execution, keyed by node name with the node's state-delta as value. The helper folds those deltas into a final_state dict so the caller gets the same shape ainvoke would have returned, plus a progress dict of shape {"current_node": str, "completed": [str, ...], "total": int}.

Two production-grade details elevate this helper above a vanilla astream loop:

Sticky _error. Once any child node has set _error in its state delta, later deltas from sibling nodes are filtered to not carry their own _error key — the first failure wins. Without this guard, a parallel branch could overwrite a real upstream failure with a partial-state success, and the supervisor's conditional edge at synthesize would route to notify-complete instead of notify-error. The two-line filter (if delta.get("_error") and final_state.get("_error"): delta = {k: v for k, v in delta.items() if k != "_error"}) is the entire mechanism.

aclose() on early exit. The async iterator is held in an explicit stream variable specifically so a try/finally can call aclose() on parent-task cancellation, timeout, or client disconnect. Without it the subgraph keeps issuing LLM calls and DB writes after the parent has already moved on — every cancellation pays for compute the user will never see. The aclose() is wrapped in its own try/except because best-effort close-on-exit must never raise; if cleanup fails, the parent task's original exception is the one the caller needs to see.

Progress accounting uses an explicit business_nodes: frozenset[str] allowlist passed in by the caller. Bookkeeping nodes (notify-complete, notify-error, the v2 load_cached_outputs) are excluded from the total so the badge reads "7 of 8 done" instead of "10 of 14 done" with bookkeeping noise inflating the denominator. The supervisor decides which nodes are "business" nodes; the helper does not guess.

Anatomy of paper_author_interview: The Longest Reach in the Fleet

Most graphs in lead-gen stop at "produce a draft, hand it to the operator." The paper_author_interview graph does not stop — it composes, dedupes, sends, and logs. It is the only graph in the fleet that actually puts mail on the wire to an external recipient without a human approval gate in between, and the care taken in its node design reflects that responsibility.

Six nodes run sequentially: load-paper-and-authors, match-emails, filter-already-sent, compose-emails, send-emails, and persist-log. Load reads the paper row and its author list from the database. Match-emails is the most interesting node and the one worth dwelling on. Compose-emails calls the email-compose drafting graph once per author. Send-emails fires the actual SMTP delivery through the Resend API. Persist-log writes every send attempt to the contact-emails table along with terminal status, message id, and any error string.

Match-emails runs a three-pass resolver. Pass zero is a synthetic short-circuit: if an author entry already carries a populated email field — because an upstream graph like find_peer_reviewers enriched it via the contact-enrich-paper-author flow — match-emails trusts it and tags the source as preloaded. Pass one consults a caller-supplied name-to-email map, normalizing the caller's keys through the same name-normalization helper that the scholar-discovery graph uses so case differences and diacritics do not cause misses. Pass two falls back to a database lookup against the contacts table: it builds a sorted-deduped set of normalized name keys for every author still unresolved after pass one, executes a single batch SQL query that normalizes the contact-table side the same way (lowercased, trimmed concatenation of first and last names), and merges the results back into the email map. Authors with no match after all three passes land in a skipped list with the reason no_email_provided.

The _email_source tag — preloaded, caller-map, contacts-table — is stamped onto every matched author for auditability. When an operator asks "where did this email address come from for this run?" the answer is in the tag, not in a separate lookup. That kind of provenance instrumentation costs almost nothing at write time and pays for itself the first time it answers a deliverability question.

Filter-already-sent is the second deduplication gate. It walks the matched-author list and drops anyone in a terminal state for this specific paper: already sent, already replied, already bounced, already unsubscribed, already opted out at the company level. The check is paper-scoped rather than universal — an author who replied to a different paper interview last month is still a valid recipient for this paper, but the same author should not receive the same paper twice. The gate runs after match-emails on purpose, so the dedup query has resolved email addresses to compare against rather than name strings.

Compose-emails delegates to email_compose_graph once per remaining author, awaiting the three-node drafting flow (gather-context, draft, refine) and collecting each draft into a per-author dict. Send-emails fires the drafts through Resend's HTTP API with a bounded-concurrency wrapper capped at three in-flight sends — even though the recipient list is usually short, the cap exists to keep a recipient list of forty authors from saturating the email-provider rate limit. Persist-log writes the final ledger: contact id, paper id, subject, body, status, Resend message id, and any error.

The graph is registered in only one place — paper_author_interview — but it gets called from several upstream graphs that all want the same downstream behavior: the lead-papers graph that surfaces papers worth interviewing about, the find-peer-reviewers flow that fans out across a target list, and direct manual invocations through the GraphQL surface. None of those callers reimplement the email-matching dance, the already-sent dedup, or the Resend bounded-concurrency wrapper — the shared graph owns them once.

The gh_patterns Graph: Five Subcommands in One Multiplexed Module

The gh_patterns graph is the Python port that retired the Rust crates/gh package in early 2026. It is the only graph in the fleet that ships as a single LangGraph carrying a multiplexed command parameter, where the entry node reads command off state and dispatches to one of five subcommand-shaped sub-flows. That shape exists because the Rust crate it replaced shipped each subcommand as a separate binary, and the team wanted the Python rewrite to preserve subcommand granularity without polluting the registry with five almost-identical assistant ids.

The five subcommands are scan-orgs, match-paper-authors, scrape-contributors, export-contributors, and search-candidates. Scan-orgs walks organizations stored in Neon or discovers new ones through topic search, then populates pattern scores on the companies table — does this org use Python, does it ship LangGraph, does it have a recent release in the AI space. Match-paper-authors is deterministic: it scores a list of GitHub logins against a contact's known papers, picks the likeliest match, and writes the login back to the contact row with no LLM involved. Scrape-contributors hydrates the contributors on AI-tagged repos through the GraphQL endpoint, computes BGE-M3 embeddings of their bios and pinned-repo descriptions, and persists everything to a contributor-embeddings table with a pgvector column. Export-contributors lifts the high-scoring rows from the embeddings table into the canonical contacts table so the downstream outreach pipeline can pick them up. And search-candidates is the multi-channel sourcing entry: it runs bio search, stargazer mining, contributor mining, org-members lookup, and network expansion in sequence, hydrates the resulting candidates, scores them, and exports the winners.

Five tactical replacements distinguish the Python port from its Rust predecessor. Candle BERT embeddings were replaced with BGE-M3 served from a local Rust-and-Candle HTTP server running on port seventy-seven-ninety-nine; the Python module calls it as an internal service rather than embedding inside the Python process, so the embedding work stays Rust-native but the orchestration moves up to Python. The LanceDB contributor store was replaced with two Postgres tables — gh-org-patterns and gh-contributor-embeddings — each carrying a pgvector column for ANN search. The async sqlx queries became plain psycopg in autocommit mode, matching the rest of the leadgen-agent codebase. The reqwest HTTP client became httpx async-client. And the dedicated GraphQL client library was replaced with raw httpx POSTs against GitHub's GraphQL endpoint, which kept the dependency surface narrow at the cost of writing query strings by hand.

The retry schedule is a fixed-tuple back-off — one second, two seconds, four seconds — applied to GitHub API failures classified as transient. That matches the broader rule in the team's user memory: prefer GraphQL batch queries over REST for GitHub interactions, and use a personal-access-token loaded from the local environment rather than an OAuth flow. The graph honors both GITHUB_TOKEN and GH_TOKEN env vars at startup, raising a clear error at first use if neither is set rather than failing on the first API call with a generic 401.

The architectural lesson from this port is not in the replacements list — it is in the multiplexed-command structure. Most LangGraph tutorials assume one graph per task. When a Rust crate's five-binary surface lands in a Python registry, splitting it into five graphs blows up the registry without changing the call sites; folding it into one graph with a command parameter preserves the audit trail and keeps the registry clean. The trade-off is that the one graph's state typed-dict has to be a union of every subcommand's input shape, but with total=False that just means each subcommand reads the fields it cares about and ignores the rest — a price the team was happy to pay.

The Auto-Apply Loop: Lead-Gen's Only Claude Sonnet User

Most graphs in the fleet run on DeepSeek. The auto-apply loop is the lone exception: it calls Claude Sonnet four-point-six through the Anthropic SDK directly, and it is the only place in the codebase where the make_sonnet helper is used. The reason is not "Sonnet is better at this task" — it is "Sonnet ships prompt caching and the auto-apply loop's resume prefix is exactly the shape prompt caching wants to amortize."

The loop runs as a single LangGraph with nine business nodes. Discover pulls open job postings from one or more sources, with the Hacker News Algolia "Who's Hiring" thread as the default primary source. Prioritize keeps the discovered order for now — Hacker News returns roughly by comment recency, which is close enough to "freshness order" that a custom sort would add complexity without information. Batch-score sends every pending job to Claude Sonnet in chunks, scoring each one against the operator's resume. Pop-next dequeues one job at a time into per-iteration scratch state. Fetch-JD reads the full job-description page when the listing summary is too thin. Score short-circuits using the batched score from earlier when one is present, falling back to a per-job call otherwise. Generate-application drafts a cover letter through the same Claude Sonnet client. Submit-application or skip writes to the ATS or marks the row skipped. Persist commits the decision to the database. And then the loop either pops the next job or terminates once it has hit the maximum-applications cap, which defaults to five.

Two numbers in this graph matter. The default fit threshold is fifty-five out of one hundred; below it, jobs are scored, recorded, and skipped. The default maximum applications per run is five. Operators tune both knobs via state fields rather than env vars, because the auto-apply loop is invoked from a Make target and the operator already wants per-run overrides.

The cache-control trick is what makes Sonnet economically viable here. The batch-score system prompt plus the operator's resume — a static prefix that does not change across jobs in a single run — is marked with cache-control set to ephemeral on the Anthropic API. Every chunk after the first hits the cache-read rate at ten percent of input pricing. A run that scores fifty jobs across five chunks pays full-input pricing exactly once and the discounted ten-percent rate for the other four chunks. The per-job cost drops by roughly seventy percent compared to a per-job call, and the latency drops because the cache hit also shortcuts upstream tokenization.

Three deduplication rules guard the loop against double-submitting. First, an already-applied URLs set is loaded from the database and any pending job whose URL is in the set is dropped at discover time. Second, a blocked-companies set — companies that have already received three or more applications historically — drops by name match, case-insensitive. Third, a per-company-per-run cap of one prevents the loop from applying to two openings from the same company in the same run, even if both pass scoring. The first two rules survive across runs; the third resets each run because the operator might genuinely want to apply to a different role at the same company on a different day.

The submitter layer is structured as a per-ATS adapter — greenhouse, lever, workable, plus a generic fallback — each implementing a small contract: parse the application form, fill the required fields from a static profile, attach the resume and the generated cover letter, and submit. Playwright drives the page; cookie-consent dismissals are handled with an explicit evaluate-and-click pattern because the standard wait-for-selector approach times out on cookie banners that ship behind a CSS animation. The ATS adapter pattern is the auto-apply loop's contribution to the broader system architecture: when a new ATS shows up, you drop in a new module and register it; no other graph code changes.

Stage E: Cross-Container Composition

Subgraphs in the same process share memory, a checkpointer, and a deploy cadence. Cross-container composition gives up all three in exchange for independent deploys. The patterns in this stage are what make that trade survivable.

Pattern 3: RemoteGraph Across Container Boundaries

Lead-gen splits compute across four independent containers:

leadgen-ml — JobBERT skill NER, BGE-M3 embeddings.
leadgen-research — Common Crawl, Arxiv/OpenAlex scholar fetchers, agentic search, GitHub pattern miners.
leadgen-scrape — Playwright-based consultancy profile scrapers, walking the Clutch.co sitemap across thousands of profile targets.
leadgen-outreach — hosts exactly one graph, paper-author-interview, split out from core so a long Resend send batch cannot starve other graphs on the shared instance. The container uses a Mistral-7B email LoRA via Cloudflare Workers AI, not DeepSeek — an operator-mandated isolation that also keeps the paper-author-interview traces in their own LangSmith project.

The main backend reaches each one through langgraph.pregel.remote.RemoteGraph, treated like any other subgraph but invoked over HTTP. The adapter lives at core/remote_graphs.py and wraps every adapter with a per-host circuit breaker that opens after five consecutive failures and holds for thirty seconds before allowing a single-shot half-open probe. The breaker is keyed by adapter name through _CircuitBreaker.for_name(...) so multiple adapter instances pointing at the same host share state. Callers get a typed RemoteUnavailable exception instead of waiting on a dead socket, which lets supervising graphs route to a degraded path instead of stalling the whole run.

The adapter does three things the stock RemoteGraph does not. First, it constructs its own LangGraphClient via get_client(url, headers, timeout=...) so the SDK's 300-second read default cannot wedge a long-running graph node — every adapter passes an explicit TimeoutTuple covering connect, read, write, and pool acquisition. Second, it wraps ainvoke in an exponential-backoff retry loop (base 0.5s, cap 8s, up to three attempts) so transient 502s do not surface as run failures. Third, it ships an aclose() that reaches into LangGraphClient.http.client and closes the pooled httpx.AsyncClient, wired into the FastAPI lifespan via aclose_all_adapters() so a deploy does not leak sockets.

The half-open probe deserves a callout. When the cool-down elapses, the breaker allows a single call through with the attempt budget capped to 1 — not the usual 3. The rationale lives in the source: a flaky remote that recovers briefly and then fails again will burn the entire retry budget on every recovery window if you let the probe retry. Capping the probe to one attempt keeps the breaker bouncing between open and closed cheaply.

The contact-enrich graph is a good study. Its extract-skills node pulls the JobBERT adapter from the configurable section of the runtime config, rather than from a module-level import. The node accepts state and config, looks up the adapter on the configurable dict, and if no adapter is present it returns an empty dict and the downstream graph keeps running on a non-ML path. If the adapter is present, the node walks the papers array on state, gathers up to ten abstracts or summaries, truncates each to five hundred and twelve characters — JobBERT's tokenizer limit — and calls the adapter through a pydantic input contract. Each successful response is validated through a matching output contract before its spans are extended into the result, and any exception in a single text is swallowed so one bad input does not poison the batch. Finally the node deduplicates the spans, lowercases them, and keeps only spans whose confidence score is at or above zero point seven.

This pattern carries five lessons worth lifting. The adapter is injected via config["configurable"] rather than a module-level import to break a circular import — core.remote_graphs already imports from leadgen_agent, and a top-level import the other way would deadlock the module loader on cold start. When the adapter is absent the node returns {} instead of raising, so the supervising graph can keep running on the LLM-only path without a try/except on every caller. The text payload is truncated to 512 characters because that is JobBERT's tokenizer limit; the node also caps the number of texts at ten to bound per-run latency. The pydantic JobbertNerInput/JobbertNerOutput contracts in leadgen_agent.contracts are the same types the remote graph validates on the receiving side, so a schema drift surfaces at the adapter boundary instead of as a JSON decode error inside the worker. And the score >= 0.7 filter deduplicates noisy low-confidence spans before they touch the database — JobBERT happily emits ten matches per abstract; the supervisor only wants the confident ones.

Unit tests benefit incidentally: they can pass a stub adapter via config without monkey-patching anything. But that is a happy side effect, not the original motivation — the circular import is.

Pattern 7: Background Tasks with Graceful Drain

The POST /threads/{tid}/runs endpoint launches graphs as fire-and-forget background tasks stored in an async-runs dict and exposed for polling. On shutdown, the FastAPI lifespan hook drains them with a twenty-second deadline (GRACEFUL_SHUTDOWN_S, env-overridable) — anything still running past that bound is cancelled. The drain set is the union of three task buckets — _async_run_tasks, _positioning_inflight, and _lead_gen_inflight — so semaphore-bounded dispatchers (POST /dispatch/positioning-all, POST /dispatch/lead-gen-teams) participate in the same drain as raw /threads/{tid}/runs background runs. The twenty-second bound is tuned against Cloudflare Containers' SIGTERM grace window (~30 seconds); leaving the container 10 seconds of headroom for checkpointer.setup cleanup and httpx client teardown is the difference between "Vercel rolled the deploy and nothing finished" and "the graph that was halfway through synthesis got a chance to commit its checkpoint." If you build long-running graphs behind a stateless HTTP frontend, you need this layer too.

The make_llm() Factory and Tier Routing

Every LLM client in the fleet is built through a single factory: make_llm(temperature, provider, tier) in leadgen_agent/llm.py. Two convenience wrappers handle the common cases — make_deepseek_pro() (tier="deep") and make_deepseek_flash() (tier="standard"). Both default to deepseek-v4-pro; the standard tier exists so deployments can independently override via DEEPSEEK_MODEL without touching the deep-tier model. The factory is cached with functools.lru_cache(maxsize=8) keyed by (provider, tier, round(temperature, 3)) — the temperature is rounded so float-noise (0.2000001 vs 0.2) does not blow the cache.

Three providers are wired:

provider="deepseek" / provider=None — DeepSeek's public API, or the proxy set via DEEPSEEK_BASE_URL. tier="deep" flips on thinking mode plus reasoning_effort=high; tier="standard" hits the regular chat endpoint. Both honor max_tokens and response_format={"type": "json_object"}.
provider="email_llm" — Cloudflare Workers AI proxy backing the email-outreach drafting graph, running Mistral-7B-Instruct-v0.2. Workers AI does not honor OpenAI-style JSON response format, so the supports-json-mode check returns false for this provider and the response goes through a regex-extract plus json-repair fallback. This is the only provider in the fleet that cannot do native JSON mode, and forgetting it is a common cause of "the outreach graph works on my laptop but five-hundreds on Workers." Note that the longer-form email_compose_graph is a separate graph and uses DeepSeek's standard tier, not Workers AI — the two graphs share a topic but not a provider.
provider="anthropic" (via make_sonnet) — Claude Sonnet 4.6 via anthropic.AsyncAnthropic, used exclusively by the auto-apply local loop in leadgen_agent/auto_apply. The Anthropic SDK client is reusable across requests, so temperature is passed at messages.create time rather than client init — the _make_sonnet_cached shape mirrors the DeepSeek factory only to keep the surface uniform.

max_retries=0 is non-negotiable on every constructed client. The OpenAI SDK's default max_retries=2 runs underneath the retry loop inside ainvoke_json_with_telemetry, which itself runs three attempts — leaving the SDK default in place turns one user-visible retry into a nine-attempt storm against a flaky upstream. The boot-time disable is small but load-bearing.

Pricing is wired through MODEL_PRICING, a dict[str, dict[str, float]] keyed by model name with input_per_1m and output_per_1m slots. DeepSeek entries are derived from a DEEPSEEK_MODELS catalog earlier in the same file so a price change updates one source of truth; other providers (CF Workers email-llm) are listed as literals. Cache-hit and off-peak discounts are not factored in — _cost_usd() returns the pessimistic price, which means real billed spend is always ≤ the computed cost_usd field in telemetry. Close enough for "which node is expensive" questions; not close enough for invoicing.

Stage F: Deployment and Operations

Every pattern so far runs inside a request. The next stage is everything that wraps the request — how containers boot, how runs are dispatched, how webhooks fire, how cron schedules trigger, and what the whole system costs to operate.

Lifespan: How a Cold Start Actually Boots

The core/app.py lifespan context manager is roughly two hundred lines and runs in a strict order on every cold start. Reading it top to bottom is the fastest way to understand why the container behaves the way it does:

1. Diagnostic state primed first. Three app-state slots — boot log, lifespan error, checkpointer alive — are populated before anything can fail. The whole lifespan sits inside a try/except that captures the traceback into the lifespan-error slot so the debug-state endpoint returns the failure over HTTP instead of crashing uvicorn. CF readiness probes hit debug-state, not /ok, because /ok proves the container exists but not that it can serve a graph.
2. LangSmith config validation. init-langsmith reads the API key and endpoint URL, logs either langsmith-ready or langsmith-disabled, and never raises. Per-call instrumentation activates only when the tracing env var is set, so a misconfig surfaces as missing traces, not as failed runs.
3. Database URL resolution. DATABASE_URL is read with a fallback to NEON_DATABASE_URL. In production both arrive from the worker entrypoint, which resolves the Secrets Store binding. Locally the value comes from the gitignored env.local file. If both env vars are blank the lifespan raises a deliberate fail-fast with the Neon pooled-connection-string hint.
4. Idempotent DDL for the Chrome extension cache. ensure-linkedin-tables runs a synchronous psycopg connect with CREATE TABLE IF NOT EXISTS, pushed through asyncio-to-thread so it does not block the event loop while CF is still polling.
5. AsyncPostgresSaver pool opens. The pool enters its async-with block with a fifteen-second open timeout. If the pool cannot fill within fifteen seconds the lifespan raises and the boot log records lifespan-exception. The prepare-threshold zero kwarg is load-bearing because PgBouncer transaction-pooling mode rejects prepared statements after the fifth identical query.
6. checkpointer.setup(). Idempotent DDL for the three checkpoint tables. No-op on every cold start after the first.
7. Graph compilation. The compile-all helper walks GRAPHS and builds each spec into a compiled graph. Per-graph compile failures land in a failures dict instead of raising — one broken graph cannot poison the other sixty-three — and the boot log records the success and failure counts.
8. Remote adapter wiring. Four remote-graph adapters are constructed for the ML, research, scrape, and outreach containers, each with retry, breaker, and explicit timeouts. Missing URL env vars are logged but do not fail the boot; any graph that tries to invoke a missing adapter raises a clear error at call time.
9. Yield. Only here does uvicorn start accepting traffic. The boot log records lifespan-ready and the debug-state endpoint flips from warming to ready.
10. Drain on shutdown. When uvicorn receives lifespan-shutdown on SIGTERM, the finally clause runs the graceful drain pattern described earlier, then the pool closes cleanly.

The whole sequence is observable through GET /__debug/state — boot_log is a flat list of strings in the order above, so a hung start is one curl away from a root cause. This is the single most useful debug surface in the system and the reason the operator memory specifically calls it out: probe via the debug-state endpoint not /ok, warm containers ignore image swaps until evicted.

The Cloudflare Worker Entrypoint and the Dead-start() Gotcha

The Python FastAPI app does not run as a standalone process in production. It runs inside a Cloudflare Container, which is a Durable-Object-backed isolate that boots a real container on first request. The entrypoint is core/src/index.js — about 190 lines of JavaScript that subclass @cloudflare/containers's Container class and wire the Worker env object into the Python process's os.environ.

The default port is 8000 and sleepAfter = "4m" — after four minutes of inactivity the container is suspended; the next request resumes it. This is the reason the lifespan's boot_log matters operationally: a request that arrives ten seconds after a four-minute idle pays the full cold-start cost, and the debug-state endpoint is the only quick way to see where the boot is.

Two kinds of secrets feed into the container, and they arrive on different timelines:

Plain wrangler secrets (wrangler secret put KEY) — these land on env.KEY as ordinary strings before the CoreContainer constructor runs. They can be plumbed directly into this.envVars synchronously, which is how DEEPSEEK_API_KEY, GITHUB_TOKEN, LANGGRAPH_AUTH_TOKEN, and the cross-container internal-auth tokens get injected.
Secrets Store bindings (declared in the wrangler config under secrets_store_secrets, currently store ID ec928f4771fb4577a607a0b122e8087e) — these arrive as async binding objects. Reading the underlying plaintext requires await env.BINDING.get(). Two values currently come through this path: HF_TOKEN (for huggingface_hub uploads from the research loop) and the LangSmith API key (for tracing).

The interaction between async Secrets Store resolution and the SDK's lazy container start is the single most non-obvious thing in this entrypoint, and the codebase memorializes it inline:

The @cloudflare/containers SDK lazy-starts the container from inside super.fetch() via its private startContainerIfNotRunning(), which reads this.envVars (sync) and never calls our async start() override. So any subclass start() override is dead code from the lazy-start path.

The workaround is to resolve the Secrets Store values inside fetch before delegating to super-fetch, and to explicitly call start with the resolved envVars first. The override checks whether the container is already running; if not, it kicks off two awaited promises in parallel — one for the Hugging Face token, one for the LangSmith API key — by calling get on each Secrets Store binding. Both calls are guarded with optional chaining and an empty-string fallback so a missing binding does not crash the boot. Once both values are resolved, it merges them into the sync envVars dict and calls this-start with the merged envVars before delegating to super-fetch as usual.

A start() override in the subclass would have looked like the obvious place to do this resolution — and would have silently never run on the lazy-start path. The team learned this the hard way and the inline comment is the kind of save-future-you documentation that other code reviewers thank the author for. If you adopt @cloudflare/containers and need Secrets Store values inside your container, this is the only pattern that works today.

The scheduled handler at the bottom of the file is the cron-trigger entry. It looks up the cron expression in a small if-elif ladder, maps it to a job name, and POSTs http://internal/cron/tick over the service binding with Authorization: Bearer ${env.LANGGRAPH_AUTH_TOKEN}. The console.log summary that follows lands in wrangler tail so operators can confirm a fire without scraping container logs.

The async-runs Polling Contract

The POST /threads/{tid}/runs endpoint is the fire-and-forget half of the LangGraph SDK protocol — the frontend uses it whenever it wants to start a graph without holding an HTTP connection open through the whole run. The endpoint mints a random run_id, writes a record into the module-level _async_runs: dict[str, dict[str, Any]] = {}, and launches _run_graph_bg as an asyncio.create_task. The task is tracked in _async_run_tasks (a set[asyncio.Task]) with a task.add_done_callback(_async_run_tasks.discard) so finished tasks self-evict and the drain set described earlier stays accurate.

The record schema is intentionally small. Each entry holds the thread id, the assistant id, a status that starts at running and transitions to either success or error, an output slot that starts null, and an error slot that also starts null. That is the whole shape.

GET /threads/{tid}/runs/{run_id} reads the record back. Three corner cases are worth knowing:

1. Unknown run after restart. If the container restarted between the POST and the GET, _async_runs.get(run_id) returns None. The endpoint returns {"status": "unknown", "thread_id": thread_id, "run_id": run_id} with a 200 — not a 404 — so the Next.js stale-run sweeper can transition the row to error without special-casing HTTP status. This is a deliberate divergence from REST norms; the contract is "tell me what you know," not "is this run alive."
2. Thread/run mismatch. If a run_id exists but its stored thread_id does not match the URL segment, the endpoint raises 404. This guards against frontend bugs that splice the wrong thread id into a poll URL.
3. Error path with webhook fallback. When _run_graph_bg catches an exception (anything except CancelledError, which it re-raises), it sets record["status"] = "error" and record["error"] = str(e)[:1000], and fires notify_error(payload, str(e)) through the project's notify webhook. Without that webhook fire, clients that opted into webhook_url would wait forever for an error signal — they only poll for status flips, and the status flip on its own is silent. The webhook delivery is wrapped in its own try/except so a flaky webhook target cannot poison the run record.

Because async-runs is in-process state, a container restart loses every in-flight run. That is the entire reason the frontend has a stale-run sweeper and why every record carries enough information (assistant_id, thread_id, original input is recoverable from the Postgres run row) for the sweeper to mark orphans. There is no Redis between the frontend and the backend — the cost-to-benefit on that piece of infrastructure has not pencilled out.

The notify-complete / notify-error Webhook Contract

The five graphs that are launched async (product-intel, analyze_product_v2, deep-competitor, pricing, gtm) all end at a terminal node that POSTs to a gateway webhook. The notifier lives in leadgen_agent/notify.py and is the connective tissue between a finished LangGraph run and the rest of the platform: it is what flips product_intel_runs.status, patches the products jsonb column for the run kind, and broadcasts to subscribed WebSocket clients through the gateway's JobPubSub Durable Object.

The contract is small but load-bearing. Each launched graph carries three keys in its state:

webhook_url — the gateway's /internal/run-finished endpoint
webhook_secret — used to compute an HMAC-SHA256 signature over the raw JSON body
app_run_id — the gateway-side run row id (separate from the LangGraph run_id in async-runs)

The frontend's startGraphRun helper in src/lib/langgraph-client.ts populates these three keys before invoking the graph. When they are absent — synchronous runs-wait endpoint invocations, unit tests with pre-populated state — the notify nodes return {} and the graph terminates without firing anything. This dual-mode behavior (gateway-aware async vs. gateway-blind sync) is what lets the same graph be called from a notebook and from production without code branches.

The HMAC signing path is direct. The post helper computes an HMAC-SHA256 over the raw JSON body using the secret as key, then opens an httpx async client with a ten-second timeout and posts the body to the webhook URL with two headers: a content-type of application/json, and an x-signature header carrying the hex digest. The gateway recomputes the HMAC over the received body and rejects mismatches. The secret lives only in state and the gateway's environment — neither end ever logs it.

Two defense-in-depth details are worth lifting. _build_payload walks an ordered tuple of _OUTPUT_KEYS = ("report", "pricing", "gtm", "icp") and picks the first non-empty key as the output payload. The ordering is deliberate: a graph that fills both report and pricing is a synthesizer, and the report key is the operator-visible artifact. A graph that only fills pricing is a leaf and reports that. The first-hit-wins rule means leaf graphs and synthesizers can coexist in the same notify path without negotiating.

_scrub walks the output dict recursively and drops keys in _PRIVATE_KEYS = {"webhook_url", "webhook_secret", "app_run_id", "tenant_id", "lg_run_id", "lg_thread_id"} so infra plumbing never leaks into the publicly-readable products jsonb. The pydantic schemas (PricingStrategy, GTMStrategy, ProductIntelReport) already whitelist serialized fields, but the recursive scrub guards against accidental pass-through from graph_meta dicts or from looser state blobs that bypass the schemas. Defense-in-depth at two layers, because the cost of one leak is much higher than the cost of two redundant filters.

The HTTP call is fire-and-forget with a ten-second timeout. Non-2xx responses are logged as warnings and the node returns {}; a failed gateway POST never crashes a graph node. The DB writes earlier in the graph (in write_rationale / draft_plan / synthesize_report) are the truth for products jsonb — the gateway's patch is defense-in-depth so a missed webhook does not lose data, just delays its broadcast.

A separate update_progress helper writes a lightweight JSON snapshot to product_intel_runs.progress (migration 0063) on each node's entry. Vercel polls productIntelRun(id).progress from the browser, which avoids opening a direct LangGraph connection from a public origin. Progress writes are fire-and-forget too; the DB work runs through asyncio.to_thread because the rest of the graph modules use the sync psycopg v3 driver and mixing async drivers across one transaction is the kind of subtle bug nobody wants to debug at 3am.

Cron: One Endpoint, Six Triggers, Seven Named Jobs

Scheduled work in lead-gen does not run as separate Cloudflare cron triggers per job. Instead, a single POST /cron/tick endpoint takes a {"job": "<name>", ...} payload and dispatches to the named handler. The Worker's the wrangler config declares six cron expressions; the scheduled handler in core/src/index.js maps each expression to a job name and POSTs the cron-tick endpoint over the service binding (getContainer(env.CONTAINER).fetch(req)) with the LANGGRAPH_AUTH_TOKEN bearer. The Python endpoint is authenticated through the same middleware as the runs-wait endpoint.

The Worker-side mapping is deliberately dumb — all logic lives in the cron module on the Python side. The cron expressions in production cover seven explicit slots in the schedule, every one of them on an off-minute so the fleet does not stack against the cron-storm that hits Cloudflare on round-minute fires. The daily Ashby delta ingest runs at six-seventeen UTC. A weekly Monday slot at six-forty-seven UTC fires the same job in full-refresh mode against the known board list. Every six hours the country-classify mop-up fires at twenty-three past the hour. Every four hours the remote-classify job runs at thirty-seven past. Weekly Sundays at six fifty-seven UTC the sales-tech enrichment runs as the heaviest catalog job. Every hour at thirteen past, a checkpoint prune sweeps Neon's checkpoint tables and keeps only the latest entry per resumable thread. And weekly Sundays at two thirteen UTC, the consultancies-weekly job fans out to the scrape container for the Clutch.co crawl.

The dispatcher's branching ladder also carries a fallback behavior worth knowing: any unrecognized cron expression silently maps to Ashby nightly with full-refresh off. New triggers added in the wrangler config without a matching branch will fire Ashby nightly until the mapping is updated — annoying if you forget, but it fails toward the safest job in the catalog rather than dropping the fire silently.

The research-loop-tick job is not in this table because its CF trigger was retired (see job catalog below). The endpoint still serves it; just no longer from a CF Worker schedule.

Seven jobs are registered today:

ashby-nightly — pulls open requisitions from the Ashby ATS, runs them through the recruitment-intent classifier, and writes back tier verdicts. The full_refresh flag rebuilds the whole ashby_jobs snapshot rather than the day's deltas.
country-classify-nightly — runs country_classify_bulk_graph against every company missing a confident country field. Pulls Brave Search snippets when the registered address is ambiguous.
remote-classify — scores remote-work compatibility for newly enriched companies using the JobBERT skill NER output plus rule-based heuristics. Writes to companies.remote_compatibility.
enrich-sales-tech — fans out across the enrich_sales_tech_graph to detect HubSpot, Salesforce, Marketo, Outreach, and other sales stack tells. Drives the ICP sales_tech_fit score.
checkpoint-prune — sweeps checkpoints, checkpoint_blobs, and checkpoint_writes for orphan rows older than the retention window. This is the safety net behind the resumable=False registry default — even with most graphs writing no checkpoints, the few that do still accrete rows over time.
research-loop-tick — the replacement for the retired crates/papers Rust pipeline. Reads seed_slug (default "sales-leadgen") and seed_query (default "sales lead generation AI"), advances the research loop one step (gap detection, paper drafting, publish gate), and stamps synthesized_papers.published_at on success. force_synthesis and force_train short-circuit specific gates for ops-driven re-runs. The handler still lives in the Python cron-tick endpoint, but the Cloudflare cron trigger for it was removed — the loop is now driven externally by make research-loop, which runs the deepseek-loop CLI and POSTs the cron-tick endpoint directly with a bearer token. Alongside this Python coordinator, a sibling Rust container called lead-gen-research-pipeline carries the heavy lifting — a standard-three Cloudflare Container running a five-lane threading model with tokio for I/O, rayon for CPU work, twenty-four IO workers wide and a sqlx pool of twenty connections to Neon, plus a Workers AI Mistral-seven-billion fallback for the DeepSeek balance-exhausted case. The Python LangGraph coordinates; the Rust container does the compute.
consultancies-weekly — the one cron handler that fans out across container boundaries. It pulls the consultancy_pipeline adapter from app.state.remote_adapters and invokes it on leadgen-scrape. If SCRAPE_URL is unset at boot, the adapter is missing and the endpoint returns 503 rather than 500 — a deliberate distinction so operators can tell "configuration is wrong" from "the scrape container is on fire." The payload accepts sitemap_count (default 44, the number of sitemap hosts to crawl) and send_emails (default true, gates outbound delivery for dry runs).

All seven handlers share the same return shape: a JSON object with ok: bool plus job-specific fields. The endpoint returns 200 when ok is true and 500 otherwise — never raises — so the cron Worker can rely on plain HTTP status for retry-vs-alert decisions.

Frontend ↔ Backend Handshake

The frontend half of every graph call lives at apps/lead-gen/src/lib/langgraph-client.ts. It is a single typed HTTP client that wraps fetch around POST ${LANGGRAPH_URL}/runs/wait with a JSON body of the shape { assistant_id, input }. The client is symmetric across local dev (http://127.0.0.1:8002, served by langgraph dev) and production (the CF Container hostname); only the LANGGRAPH_URL env var changes.

Four pieces of the client are worth lifting because they encode contracts the backend cannot enforce on its own:

Status classification before bubbling errors. classifyStatus(status) maps HTTP status into a five-value LangGraphErrorKind discriminator — "auth" | "timeout" | "backend" | "client" | "unknown". UI code can then decide to show a "session expired" banner on auth, surface a "model is slow" toast on timeout, or just kick the global error boundary on backend. Without this classification step, the frontend would have to grep through error messages — a recipe for fragility as backend error strings drift.

Body sanitization across two error shapes. The client knows about two error envelopes: FastAPI's {"detail": "..."} and the Cloudflare dispatcher's plaintext "invalid bearer token". sanitizeBody() tries to JSON-parse first and falls back to truncating raw text at 500 characters. The dispatcher distinction matters — when the backend container is healthy but the dispatcher rejects the bearer token, the response never reaches FastAPI's exception handler at all, so the error body comes from a different layer with a different shape.

Production missing-token alarm. warnIfMissingTokenInProd() logs once per session if LANGGRAPH_URL points at anything other than 127.0.0.1/localhost while LANGGRAPH_AUTH_TOKEN is unset. This guards a specific deployment failure mode: a Vercel deploy that promoted LANGGRAPH_URL but not the token secret would 401 on every graph call with no obvious signal in the logs. The single console warning is what makes "everything is broken" diagnosable in seconds.

V1/V2 selector on productIntelAssistantId(). A small env-gated function returns "analyze_product_v2" when PRODUCT_INTEL_GRAPH_VERSION=v2 and "product_intel" otherwise. Default is "v1". This is the frontend half of the dual-supervisor cutover described in the subgraph-composition pattern — the backend ships both assistants in the registry, and the frontend toggles which one it calls via env without redeploying. The result is a zero-downtime A/B path that lets ops roll v2 forward in production and roll back instantly if the parallel DAG misbehaves.

The default timeout is sixty seconds (AbortSignal.timeout(60_000)), overridable per call. Callers that need to wait on heavy graphs (product-intel end-to-end, deep-competitor with five parallel scrapers) pass timeoutMs: 180_000 and rely on the backend's own graceful drain to commit checkpoints if the timeout fires.

The client's top-of-module comment still mentions five graphs — documentation drift from when the local-dev registry only exposed five entries. The runtime is generic and does not validate the assistant id against any list, so the stale comment is harmless beyond first impressions.

Stage G: Capstones

That is the system end to end. What remains is the meta-layer — the failure modes the codebase already documents inline, the five design moves that repeat across the fleet, and how to read the whole thing as an AI Product Engineer at a whiteboard.

Common Failure Modes the System Already Documents Inline

Lead-gen has accumulated a small catalog of subtle production failures that show up in the code itself as inline comments and as feedback-memory entries. Listening through this catalog is one of the fastest ways to absorb the genuinely hard-won lessons embedded in the codebase.

The most insidious one is the LangGraph typed-dict drop. When a graph node returns a dict that includes a key not declared on the state typed-dict, LangGraph silently discards that key on the way to the next node. The graph still completes; the run still reports success; the downstream node observes the field as missing. The symptom is status success with empty output — the exact failure mode the debugging walkthrough is built around. Every state class in the fleet carries an explicit comment naming the declared fields, and the auto-apply graph's docstring writes the rule in capital letters. The fix is mechanical once the failure mode is recognized; the recognition is the hard part, because there is no exception, no log line, no signal beyond "the next node thinks nothing arrived."

The next one is the prepare-threshold gotcha against PgBouncer. The Neon pooler runs PgBouncer in transaction-pooling mode, which does not support PostgreSQL prepared statements. The default psycopg-pool behavior caches prepared statements after the fifth identical query — at which point PgBouncer rejects the next execution with an invalid-sql-statement-name error. The fix lives in the connection-pool kwargs: passing prepare-threshold equal to zero disables the caching entirely. Forgetting it means the container looks healthy through the first four runs and starts five-hundred-ing on the fifth, which is the kind of failure shape that makes ops chase a phantom rate-limit before finding the real cause.

The third is the Cloudflare-containers SDK dead-code subclass-start override, already covered when the article walked through the worker entrypoint but worth lifting again here because it is the lesson most easily lost in the file's two hundred lines. The SDK's lazy-start path inside super.fetch() reads this.envVars synchronously and never calls the subclass start override. A start override looks like the obvious place to resolve Secrets Store bindings — and would never run on the lazy path. The workaround is to do the async resolution inside fetch() itself, ahead of super.fetch(), and to call this-start explicitly with the resolved env vars.

A fourth is the discovery-graph blocklist bypass described in the company-discovery walkthrough — the LLM-brainstorm path needs its own blocklist gate at persist time because the pipeline graph's earlier gate is on a different code path. A fifth is the retired research-loop cron trigger: the endpoint is still served by the cron-tick endpoint, but the Cloudflare scheduled trigger was removed, and any new caller assuming the cron still fires will silently see no work happen. A sixth is the server-restart race in the auto-apply loop: the already-applied URL set is loaded once at discover time, but a long-running session can have URLs land in the database between discover and pop-next, so the pop-next node re-queries to catch the gap.

A seventh is the LangGraph fan-out poisoning: hitting the local langgraph dev server on port eighty-oh-two with parallel curls causes the single-worker queue to drop requests on disconnect and leave the run in a half-started state. The fix is operational, not architectural — sequential bash loops with curl's dump-headers flag are the canonical pattern; parallel curls are forbidden in the team memory specifically because they poison the queue.

An eighth is the wrangler-deploy permissions gotcha against Secrets Store bindings. Running wrangler deploy with a Cloudflare API token in the environment errors with the message ten-thousand-twenty-one — secrets store binding authorization failed — because the API token lacks the secrets-store-read scope that the deploy flow needs to validate the bindings. The fix is operational: drop the API token from the environment for the duration of the deploy so wrangler falls back to the stored OAuth credential, which has full scope. The standard incantation is to prepend env minus-u CLOUDFLARE_API_TOKEN to the wrangler-deploy command. The deploy runbook in the team memory documents the create-secret variant of this trick; the deploy-time variant is the one operators trip on after a fresh secret has been bound but before the first redeploy lands.

The common thread across the catalog is that none of these failures throw exceptions. They all manifest as silent-success-with-degraded-behavior. That is the failure mode the debugging walkthrough warns about — and it is the failure mode that the failure-taxonomy enum was designed to make findable without grep.

A second catalog is worth lifting alongside this one: the trace-fingerprint shapes that recur in wrong-answer incident reports, each pairing an operator-described symptom with a concrete fingerprint in the LangSmith trace. The hallucination shape is the most common — tool span output correct, LLM completion contradicting it; the fix is prompt-side, either an explicit grounding rule or a tier escalation to deep with reasoning-effort high. The schema-drift shape is a tool span at error level carrying a relation-does-not-exist message; the fix is to run the Drizzle migrations and regenerate any tools-doc string that names a renamed table. The send-worker-exception shape leaves the stage report's errors array non-empty with the phase status reading partial or fail; the first error string is usually a 429, a Brave Search five-hundred, or a missing API key.

The latency-outlier shape is one phase duration ten times the others while individual LLM-call latencies stay flat — the fingerprint of transient upstream retries inside the LLM wrapper's exponential-backoff loop, visible today only via wrangler tail because the retry counter is logs-only. The prompt-cache-hit shape is the same wrong answer twice across runs with identical args and completions; the workaround is to prepend a nonce or briefly swap the model tier to invalidate the cache key. The bad-tool-selection shape shows tool inputs with a wrong table name or column reference; the fix is to tighten the tools-doc block and add a worked example. And the no-traces-appearing shape is a container that booted cleanly but produced zero LangSmith spans — the boot log will say langsmith-disabled, which means either the tracing environment variable is unset or the Secrets Store API key did not resolve.

Design Moves That Repeat Across the Fleet

Reading the seventy-five-plus graphs back-to-back, five design moves show up everywhere. They are not seven patterns in the LangGraph sense — they are smaller habits, each less than a page of code, that operate as the load-bearing connective tissue between the patterns. Naming them explicitly is the cheapest way to start spotting them in code review.

The first move is disjoint-target writes. Wherever two paths run in parallel — Send fan-out workers, supervisor subgraphs, semaphore-bounded dispatchers — each path writes to a target the others never touch. Pricing writes to its own jsonb column; gtm writes to its own; deep-competitor writes to its own table family. The result is that parallelism never requires locking and never requires the merge reducer to do anything more sophisticated than concatenation. When a new fan-out lands and the first reviewer's question is "what if two of these collide," the answer is built into the schema rather than enforced at runtime.

The second move is merge reducers for the few state slots that genuinely do need concurrent writes. The graph-meta telemetry slot is the canonical example: every node, including parallel Send workers, writes its telemetry under its own name, and the reducer folds the entries together. The reducer never makes a decision; it just spreads two dicts together. The pattern works precisely because the first move — disjoint targets — keeps the reducer cheap.

The third move is failure-as-data, not failure-as-exception. The classify-paper graph catches LLM errors and returns an off-topic verdict with the exception class embedded in the reason. The match-emails node falls through to "skipped with reason" rather than raising on a missing email. The notify-error webhook is wrapped in its own try-except so a flaky webhook target cannot poison the run record. The pattern lets supervisor graphs route on the data instead of catching everywhere, and it makes the failure-taxonomy enum and the subgraph-errors reducer the natural surface for inspection.

The fourth move is provenance tags on every join. The match-emails node tags resolved emails with their source — preloaded, caller-map, or contacts-table. The classify-recruitment graphs tag verdicts with the model name and prompt version. The compute-totals helper stamps total-cost-usd into the run row. The cost is one extra field per write; the payoff is that the first time an operator asks "where did this email come from" or "what model produced this verdict," the answer is on the row itself instead of in a separate lookup. Provenance tags pay for themselves the first time they are read.

The fifth move is dual-mode behavior controlled by a single flag rather than a separate code path. The pipeline graph's auto-confirm flag short-circuits the interrupt gate without forking the graph. The notify-complete node no-ops when the three gateway keys are absent on state, which lets the same graph be invoked from a notebook or from production without code branches. The build-graph helpers accept a None checkpointer for non-resumable graphs. The pattern is "the same code path serves both modes; one flag selects which side of the conditional runs." The alternative — two graphs, two endpoints, two code paths to keep in sync — is the failure mode the team explicitly chose against on every junction.

Naming these five moves matters more than naming the seven patterns because the moves are how the patterns get composed safely. A team that adopts the pattern catalog without the moves underneath will land in subtle concurrency bugs and silent failure modes within weeks. A team that adopts the moves first will land in the patterns naturally on the way.

Reading This System as an AI Product Engineer

The rest of this article is engineering documentation. This section reads the same systems through a different lens — the three classic questions an AI Product Engineer hears at the whiteboard: trace design for a multi-step agent, production debugging of a wrong agent answer, and alert design with threshold logic. The lead-gen surfaces covered are a near-complete worked example for the first two questions and an honest-gap example for the third; where the production system is missing infrastructure an interview answer would naturally call for, the gap is named directly rather than papered over.

If asked: design a trace for a five-call agent

Lead-gen ships three JSON-router agent loops that all share the same trace shape: admin-chat for read-only DB question-answering, capped at six steps; agentic-search for codebase search with a glob-then-grep-then-read tool hierarchy, capped at eight steps and fanning out three parallel workers by default through a decompose-and-synthesize supervisor; and the research-agent run-task loop for Semantic Scholar paper search, capped at ten steps with a house style that holds the answer until the loop has at least three strong papers in hand. The deterministic graphs trace the same way but with fixed node shapes rather than a loop. The closest example to walk through end-to-end is admin-chat. Picture a single invocation where the operator asks how many contacts were added last week. On step one the LLM emits a count-rows call against a hallucinated table name — contacts-last-week — and the dispatcher returns the literal string "Error: table does not exist." On step two the LLM recovers by calling inspect-schema on the real contacts table; on step three it emits the correct query; on step four it returns an answer. Four LLM calls, three tool dispatches, one self-correction loop.

The trace the system already captures for that run has five layers. First, every LLM call goes through the ainvoke-json-with-telemetry helper, which returns a six-field telemetry dict carrying model name, input tokens, output tokens, total tokens, dollar cost, and latency in milliseconds, plus a calls counter that increments per invocation. Second, every tool dispatch is wrapped in the tool-call-span helper from the LangSmith setup module, which records the tool name, the arguments, the attempt number, and either the result clipped to two thousand characters or the captured error. Third, the entire admin-chat loop is wrapped in an agent-run-span that stamps the maximum step count and the prompt-character budget, so the run-tree's root span carries the operator-visible question and the final answer. Fourth, the per-step accumulator in the chat node sums tokens and cost locally so the run-span's end-call carries step count plus totals — operators reading LangSmith see "this question cost twelve cents in six tool calls and never converged" without leaving the trace view. Fifth, the compute-totals helper at run termination rolls everything into the five-field aggregate that mirrors to the total-cost-usd column on the product-intel-runs table from migration sixty-six.

One gotcha worth naming in the answer: the total-latency-llm field is the sum across retries and across fan-out workers, not wall-clock. A four-step trace with one retried LLM call shows latency totals larger than the user-perceived response time. The LangSmith run-tree is where wall-clock and compute-used reconcile, because the tree shows actual span start and end times alongside the summed-up telemetry on the totals.

If asked: a user reports a wrong answer — debug it

The most common shape of "wrong answer" in lead-gen is not a flat-out wrong claim — it is a successful run with degraded output. Picture a product-intel-v2 run where the report renders but the competitor section is blank. The diagnosis walk has a specific operator order.

Start at the debug-state endpoint to rule out infrastructure problems. The boot-log array, the lifespan-error field, the checkpointer-alive flag, and the graph-compile-failures list all surface here without auth; if the container booted cleanly, all four are healthy and the issue is downstream of the lifespan. In this scenario, they are.

Next read the run record by hitting the runs endpoint with the thread id and run id. The status field is the first real signal — not because it reads "error," but because it reads "success." A successful run with a degraded section is structurally different from a failed run, and confusing the two is the most common debug-path mistake. The success status means the supervisor reached its terminal node; the missing competitor section means something inside the supervisor degraded along the way.

Inspect the final state's subgraph-errors slot. The product-intel-v2 supervisor accumulates per-branch failures into this slot through the merge-subgraph-errors reducer; the slot is keyed by subgraph name, so a deep-competitor branch that failed shows up as a dict entry naming deep-competitor with the exception string clipped at five hundred characters. That clip is enough to recognize the failure class without overwhelming the run record.

Pivot to the LangSmith trace tree. The deep-competitor branch's terminal span carries a failure-taxonomy code — one of ten enum values including hallucinated-citation, infeasible-method, claim-mismatch, budget-exceeded, external-api-failure, reviewer-pool-insufficient, heldout-regression, conflict-of-interest violation, infrastructure, and unknown. The build-failure-record helper persists the typed failure with the node name, the exception type, and a failed-at timestamp, so a SQL query against the failure-records table finds every deep-competitor failure with the same taxonomy code across the last week without rereading traces.

Close with the partial-failure contract: synthesize's conditional edge routed to notify-complete rather than notify-error because pricing and gtm succeeded, which is why the operator saw a report at all instead of a failed-run banner. A success status with degraded output is not a trace-surface bug — it is the partial-failure contract working as designed, and the taxonomy enum is what makes the degraded branch findable without grep.

One more correlation mechanism is worth naming for an interview answer: every inbound request flows through an observability middleware that mints an x-request-id as a fresh uuid4 when the header is absent and echoes it on every response, including the four-oh-ones that never reach a graph handler. The same identifier travels through Vercel logs, the Cloudflare dispatcher, the core and research workers, and the LangSmith trace's run metadata. A single wrangler tail filtered by that id stitches the entire user-visible interaction back together — which is the primitive that makes debugging across worker boundaries something other than a guessing game.

If asked: pick three alerts and justify the thresholds

The honest version of this answer separates "what lead-gen has instrumented today" from "what the alerting plane would still need." Three alerts make a strong shortlist, in increasing order of unbuilt-ness.

First, per-host circuit-breaker open transitions. This is mostly built. The circuit-breaker class in the remote-graphs module flips state after five consecutive failures and holds open for thirty seconds before allowing a single-shot half-open probe; the breaker is keyed by adapter name, so the leadgen-ml adapter, the leadgen-research adapter, the leadgen-scrape adapter, and the leadgen-outreach adapter each carry their own state. The alert would fire on the open transition with the adapter name as the routing key — five failures inside thirty seconds is the threshold the source code already enforces, so the alert inherits the breaker's own definition of "this is broken." The unbuilt piece is the emitter that takes the in-process state transition out of memory and into a notifier. Today the transition surfaces only as a log line.

Second, per-run cost anomaly. The data layer is built; the alerting layer is not. The compute-totals helper stamps total-cost-usd on every product-intel-runs row, which means the column needed to detect anomalies has been populating since migration sixty-six. A reasonable threshold reads "this run's total cost exceeds three times the rolling seven-day p95 cost for the same assistant id" — that frame catches both gradual cost creep and sudden spikes, and the assistant-id grouping means a deep-competitor run is compared to its own historical baseline rather than to a cheap classify-paper run. What does not exist is the rolling baseline computation, the standard-deviation tracking, or the wiring that turns a SQL query into a page.

Third, typed-failure-rate spike. Partially built — the data layer is the strongest of the three, the alerting layer is the weakest. The failure-taxonomy enum and the build-failure-record helper already persist typed failures with node name, exception type, and timestamp, so the alert is a SQL query over a rolling window rather than new instrumentation. A reasonable threshold reads "hallucinated-citation or claim-mismatch failures exceed five percent of runs over a rolling thirty-minute window per assistant id" — both codes are high-signal indicators of LLM output quality regression, and the per-assistant grouping prevents a noisy classifier from masking a quiet but problematic synthesizer.

Close the answer by naming the gap directly. There is no PagerDuty wiring, no Slack hook, no Opsgenie integration, no p95 latency histogram, no rolling cost baseline, no token-limit guard, no spend cap. The observability stack carries a parallel set of gaps worth listing in the same breath: no OpenTelemetry or OTLP exporter, so traces live only in LangSmith and cannot flow into Grafana Tempo or Honeycomb alongside non-LLM services; no in-app flame-graph viewer, so operators jump to the LangSmith UI for the visual and the lead-gen surface only exposes rolled-up cost and status; no Neon-side mirror of span data, so a LangSmith outage takes trace history with it; no per-tool argument redaction, so prompts, completions, and tool arguments are captured verbatim, a known PII concern on contact-enrichment traces; and no admin-UI list page for product-intel-runs, so triage across multiple runs requires either a SQL query or a Slack message with the right run id. The retry-attempt counter in the LLM wrapper is also logs-only — transient failures emit a warning to standard out but the count never lands on the telemetry dict or the tool-call span, so flaky-upstream incidents are diagnosed by tailing the worker rather than by filtering in LangSmith. And the DeepSeek deep-tier think-blocks are stripped before capture by the JSON parser, keeping prompt tokens cheap but meaning trace prompts and completions never carry the model's chain-of-thought — useful for token economy, painful when a wrong-answer report would have been diagnosed by reading the reasoning. The instrumentation exists at the data layer; the alerting plane that would turn those signals into pager pages does not. An interview answer that pretends the alerting plane already exists is worse than one that scopes what would need to be built; the right framing is here are three alerts the existing data layer supports, and here is the wiring the production system would still need to take any of them live. That distinction is the difference between an answer that sounds rehearsed and an answer that sounds like it came from someone who has actually shipped a production system.

When to Reach for This Architecture

Lead-gen's design pays for itself when:

You have many small graphs that benefit from sharing one persistence layer and one telemetry plane.
Workloads naturally fan out — many companies, many contacts, many candidates — and merge-dict reducers can collect results without coordination.
Some steps are slow, untrusted, or live in another container, and you need a circuit breaker between you and them.
A human needs to approve a subset of the work before money or messages move.

If you only have one linear graph that runs in under a minute, this is overkill. If you have an agent fleet that has to keep running while one of its arms is on fire, this is the playbook.
